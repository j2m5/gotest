# Go Test

Go API + PostgreSQL + React SPA. Авторизация использует серверные сессии в HttpOnly cookie.
Токены сессий и подтверждения email хранятся в БД как SHA-256; пароли — bcrypt.

## Запуск

Нужны Go 1.26+, Node.js 24+ с npm, PostgreSQL 14+ с ICU и базой в UTF8,
а также CLI golang-migrate для SQL-миграций. Локальные проверки выполнены на PostgreSQL 18.3.
Команды выполняются из корня проекта, кроме отмеченных команд frontend.

1. При первом запуске создайте .env по .env.example; существующий .env дополните новыми параметрами.
2. Укажите DATABASE_URL. Для обычного запуска PUBLIC_URL=http://localhost:8081.
3. Установите зависимости и примените миграции к выбранной БД:

~~~powershell
npm run setup
npm run migrate
~~~

Команда npm run migrate загружает `.env` и вызывает установленный CLI `migrate` из PATH.
Значения окружения имеют приоритет; `npm run migrate -- version` показывает текущую версию.
Для локальной PostgreSQL без TLS укажите в URL параметр `sslmode=disable`:
`?sslmode=disable` либо `&sslmode=disable`, если другие параметры уже есть.
Приложение намеренно не запускает миграции при старте.

4. Загрузите справочники, соберите приложение и запустите API:

~~~powershell
npm run seed
npm run build
npm run dev:api
~~~

Откройте http://localhost:8081/register. В режиме local письмо появится в .local/mail.
Откройте .eml почтовым клиентом, перейдите по ссылке и нажмите подтверждение.
После этого доступны вход, создание и выбор персонажа.

Для Vite dev задайте PUBLIC_URL=http://localhost:5173, запустите npm run dev:api и отдельно
npm run dev:web из корня проекта. Запросы /api проксируются на localhost:8081; при смене APP_PORT
обновите адрес proxy в frontend/vite.config.ts.

## Команды разработки и CI

Команды из корня одинаковы для PowerShell и Linux. Корневой package.json не добавляет
зависимостей: `scripts/dev.mjs` использует встроенные возможности Node.js.

| Команда | Что выполняется |
| --- | --- |
| npm run setup | go mod download и npm ci во frontend по lock-файлу |
| npm run dev:api | Go API с загрузкой .env |
| npm run dev:web | Vite; запускается в отдельном терминале |
| npm run build | Go-бинарники в .local/bin и frontend/dist |
| npm run lint | Проверка gofmt, go vet и frontend ESLint |
| npm run audit | Проверка npm-зависимостей приложения и сборки; нужен доступ к npm Registry |
| npm run migrate | Применение up-миграций; `-- version` показывает версию |
| npm run seed | Транзакционные сиды; можно передать `-- -dir ./seeds -timeout 30s` |
| npm run cleanup | Пакетное удаление истёкших сессий/email-токенов; `-- -dry-run` для предварительного подсчёта |
| npm test | Тесты команд, Go и frontend; локально допускает ненастроенные интеграционные проверки |
| npm run test:integration | SQL-тесты db/seed; TEST_DATABASE_URL обязателен |
| npm run check | lint, обе сборки и все тесты; БД и браузер обязательны |
| npm run test:db:up | Отдельная тестовая PostgreSQL через Docker Compose с ожиданием готовности |
| npm run test:db:down | Удаление только Compose-окружения тестовой БД и его данных |

Go-команды ограничены каталогами cmd/internal/tests: Go-файлы из node_modules не участвуют
в проверках. Для Go-исходников `.gitattributes` закрепляет LF, чтобы gofmt одинаково
работал после checkout на Windows и Linux. Любая ошибка команды останавливает общий запуск.

Для полного локального прогона скопируйте `.env.test.example` в `.env.test` (если файла
ещё нет) и укажите абсолютный путь CHARACTER_BROWSER_BINARY к Chrome/Chromium/Edge.
Например: `C:/Program Files/Google/Chrome/Application/chrome.exe` или `/usr/bin/google-chrome`.
Файл `.env.test` исключён из Git; переменные терминала имеют приоритет над его значениями.
Тестовые команды загружают только этот файл, без подстановки DATABASE_URL из `.env`.

Если используете Docker Desktop/Engine с Linux-контейнерами:

~~~powershell
npm run test:db:up
npm run check
npm run test:db:down
~~~

Compose поднимает PostgreSQL 18.6-bookworm с ICU и UTF8 на `127.0.0.1:55432`;
адрес и тестовые реквизиты есть в `.env.test.example`. Данные временные, в tmpfs,
и не связаны с БД приложения. Для PostgreSQL 18 используется точка монтирования
`/var/lib/postgresql`, согласно [документации официального образа](https://github.com/docker-library/docs/blob/master/postgres/README.md#pgdata).
Можно использовать отдельно установленную тестовую PostgreSQL: задайте её адрес
в TEST_DATABASE_URL, и команды Docker не понадобятся. Если переключаетесь на Compose,
убедитесь, что TEST_DATABASE_URL указывает на порт 55432 из примера.

При `CI=true`/`CI=1` даже прямой `go test` завершится ошибкой, если обязательные
TEST_DATABASE_URL или CHARACTER_BROWSER_BINARY отсутствуют. Вне CI такое поведение можно
включить отдельно через REQUIRE_DATABASE_TESTS=1 и REQUIRE_BROWSER_TESTS=1.
`npm run check` включает оба требования автоматически; ошибка соединения, запуска браузера
или отсутствие собранного frontend также приводят к ошибке, а не пропуску.

`.github/workflows/ci.yml` запускается для PR, push в master и вручную. Он использует
Ubuntu 24.04, Go из go.mod, Node из .node-version, отдельный PostgreSQL service с healthcheck
и установленный Chrome. После setup выполняются audit и та же команда check. Порт PostgreSQL
выбирается runner автоматически и передаётся в шаг проверки по
[контракту service containers GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).
Actions закреплены по SHA, права ограничены чтением репозитория; секреты и деплой не нужны.
Результаты запусков доступны в [GitHub Actions](https://github.com/j2m5/gotest/actions).

`audit` — отдельная сетевая проверка: она завершает CI с ошибкой при advisory уровня
moderate/high/critical, включая devDependencies, а также при сбое получения отчёта.
`check` сохраняет локальные проверки без обязательного запроса к реестру. Обновления
зависимостей проверяйте через чистый `npm run setup`, затем `npm run audit` и `npm run check`;
изменения frontend/package.json и frontend/package-lock.json сохраняйте вместе. Нулевой отчёт означает
отсутствие известных npm advisory для текущего дерева зависимостей на момент проверки.

## Логи и проверки доступности

API пишет JSON-логи через стандартный `log/slog` в stderr. Каждому запросу назначается
новый случайный `X-Request-ID`: он возвращается в заголовке ответа и связывает записи
обработчика с итоговым событием `http_request`. Входящий X-Request-ID не переиспользуется.
При разборе ошибки сохраните этот заголовок из вкладки Network браузера и найдите
соответствующий `request_id` в серверном логе.

`http_request` содержит method, path (без query string), status, bytes (тело ответа),
duration_ms и aborted. Для 5xx и оборванных ответов используется ERROR; остальные запросы
пишутся на INFO. Ошибка доставки письма после успешного создания аккаунта записывается
отдельно на WARN с тем же ID. Данные форм, Cookie, Authorization, query-параметры и сырые
сообщения SQL/SMTP в эти записи не включаются. Для ошибок сохраняются error_kind,
error_type и, если применимо, SQLSTATE; ошибки конфигурации содержат имя настройки и
ограничение без её значения. Путь запроса виден в логах: секреты должны передаваться
в теле или query, а не в сегментах пути.

Паника до начала ответа даёт обычный JSON 500/internal_error; стек сохраняется только
на сервере, значение паники не записывается. Если заголовки или часть тела уже отправлены,
соединение обрывается и журнал получает aborted=true вместе с фактически начатым статусом.
Ошибки запуска отмечаются событием application_failed и полем stage; http_started
появляется только после успешного открытия порта. Остановка отмечается http_stopping/http_stopped.

Проверки доступны на порту Go API без сессии и собранного frontend:

| Маршрут | Назначение |
| --- | --- |
| GET /healthz | Живость HTTP-сервера; 200 с `{"status":"ok"}`, без обращения к БД |
| GET /readyz | Ping PostgreSQL с таймаутом до 2 секунд; 200 при успехе, 503/not_ready при ошибке, остановке или отсутствии проверки |

Оба маршрута поддерживают HEAD, возвращают X-Request-ID и Cache-Control: no-store.
Например: `curl.exe -i http://localhost:8081/readyz` на Windows или
`curl -i http://localhost:8081/readyz` на Linux. Проверяйте именно порт API;
Vite проксирует только /api. Readiness проверяет соединение с БД, а миграции и сиды
по-прежнему применяются отдельными командами перед запуском.

## Очистка истёкших сессий и email-токенов

После применения миграций, включая `20261025000500_auth_expiry_indexes`, можно запустить:

~~~powershell
npm run cleanup -- -dry-run
npm run cleanup -- -batch-size 1000 -timeout 1m
~~~

Команда загружает `.env` и использует только DATABASE_URL; переменная окружения имеет
приоритет. HTTP и почтовые настройки ей не нужны. Доступен прямой запуск
`go run ./cmd/cleanup`; после `npm run build` — `.local/bin/cleanup.exe` на Windows
или `.local/bin/cleanup` на Linux. Рабочая папка определяет расположение `.env`.

В начале прохода фиксируется время PostgreSQL. Удаляются sessions с expires_at и
email_verifications с expired_at не позднее этой отметки. Каждый DELETE обрабатывает
до batch-size строк, начиная с самых старых. По умолчанию batch-size=1000, допустимо
1..10000; таблицы обрабатываются поочерёдно короткими транзакциями. Аккаунты, персонажи
и users.character_id не изменяются. Истечение сессии проверяется при авторизации
независимо от запуска очистки.

`FOR UPDATE SKIP LOCKED` пропускает записи, занятые другим запросом: они будут доступны
следующему проходу после освобождения. Записи, истёкшие уже после времени отсечения,
также остаются до следующего запуска. Поэтому успешный проход не гарантирует, что
в момент его завершения вообще нет просроченных строк. Параллельные запуски допустимы.

`-dry-run` только считает подходящие строки, включая занятые: удалений и блокировок строк
нет. Это оценка на момент проверки; она может отличаться от результата следующего запуска.
Для отбора добавлены индексы `(expires_at,id)` и `(expired_at,id)`; down-миграция
удаляет только эти индексы, сохраняя данные.

По умолчанию весь запуск, включая подключение, ограничен минутой; само подключение —
не более 10 секунд. Ctrl+C/SIGTERM или ошибка завершают команду с ненулевым кодом.
Ранее подтверждённые пакеты уже зафиксированы. При потере соединения в момент commit
исход последнего запроса может быть неизвестен, поэтому счётчики ошибки показывают
подтверждённые удаления, а не гарантированное итоговое число. Повторный запуск безопасен.

Бинарник пишет JSON в stderr: cleanup_preview содержит sessions_matched/verifications_matched,
cleanup_completed — sessions_deleted/verifications_deleted; также выводятся cutoff,
число непустых пакетов batches и duration_ms. cleanup_failed содержит этап и безопасную
категорию ошибки, а при сбое очистки — накопленные подтверждённые счётчики. Токены и
строка подключения в лог не включаются. Справка: `npm run cleanup -- -help`.

Очистка запускается отдельно от API. Автоматического расписания пока нет; для него
можно использовать собранный бинарник с тем же окружением и выбранной рабочей папкой.

## Справочники и сиды

После применения **всех миграций**, включая `20261025000200_seed_codes`, выполните:

~~~powershell
go run ./cmd/seed
~~~

Команда загружает `.env`, но использует только `DATABASE_URL`: настройки HTTP и почты
для неё не нужны. Все SQL-файлы из `seeds/` выполняются по имени в одной транзакции.
Об успешном применении файлов сообщается после commit. Ошибка, прерывание или таймаут
откатывают изменения всего запуска; пустая/отсутствующая папка и пустой SQL-файл — ошибка.

Можно задать другой путь (относительно рабочей папки или абсолютный) и общий таймаут:

~~~powershell
go run ./cmd/seed -dir ./seeds -timeout 30s
~~~

По умолчанию общий таймаут — одна минута, подключение к БД ограничено десятью секундами.
SQL-файлы сидов не должны содержать собственные BEGIN/COMMIT/ROLLBACK.

Фракции, классы и способности имеют постоянный уникальный `code`, независимый от названия
и числового ID. Связи в сидах разрешаются по кодам. Повторный запуск добавляет недостающие
записи и связи, сохраняя существующие ID, названия, характеристики и пороги опыта.
Для изменения уже настроенного баланса нужна отдельная миграция: seed его не перезаписывает.
Как и при обычном PostgreSQL INSERT, пропущенные вставки и откаты могут оставлять пробелы
в SERIAL-последовательностях; непрерывность ID не требуется.

Миграция кодов сохраняет существующие записи и ссылки на них. Старые стандартные фракции
и классы распознаются по названиям и принадлежности к фракции; способности — по сочетанию
названия и иконки, поскольку названия повторяются. Неизвестные/переименованные записи
получают коды `legacy_faction_<id>`, `legacy_class_<id>`, `legacy_ability_<id>`.
При необходимости их можно вручную сопоставить со стандартными кодами **до запуска seed**,
иначе seed добавит недостающие стандартные записи отдельно.

Если старые повторные запуски уже создали несколько записей с одним стандартным кодом,
миграция прерывается целиком с сообщением `duplicate legacy ...`. Дубликаты нужно разобрать
с учётом ссылок персонажей и справочников; автоматического удаления или объединения нет.
Down-миграция удаляет только столбцы кодов и их ограничения, сохраняя данные и числовые ID.
После неё новые сиды требуют повторного применения up-миграции.

## Аккаунт и персонажи

User — аккаунт с несколькими персонажами. Nullable-поле `users.character_id` содержит
активного персонажа, общего для всех сессий и устройств аккаунта. NULL означает отсутствие
выбора. При выходе из действующей сессии выбор сбрасывается для всего аккаунта, а удаляется
только текущая сессия; остальные устройства остаются авторизованными.

Миграция `20261025000300_character_integrity` закрепляет правила на уровне PostgreSQL:

- `(users.id, users.character_id)` ссылается на `(characters.user_id, characters.id)`:
  активным может быть только свой существующий персонаж.
- `(characters.class_id, characters.faction_id)` ссылается на соответствующую пару в classes:
  класс и фракция персонажа должны совпадать.
- `users.character_id` имеет тип INTEGER, как `characters.id`; в Go ему соответствует `*int`.
- Справочники содержат четыре базовых класса Империи и четыре Республики, без подклассов.

Чтобы удалить активного персонажа, сначала нужно сбросить выбор. Удаление всего аккаунта
каскадно удаляет его персонажей. При старых несовместимых связях миграция останавливается
целиком с диагностикой, не удаляя данные. Down-миграция снимает новые ограничения,
возвращает прежний тип BIGINT и сохраняет строки.

Миграции, меняющие типы столбцов, применяйте при остановленном приложении; после них запустите
приложение заново, чтобы соединения pgx не использовали старые подготовленные планы запросов.

Сброс активного персонажа и отзыв сессии при logout выполняются одной транзакцией.
Повторный logout с уже отозванным токеном не изменяет более поздний выбор. Истёкший токен
удаляется, но больше не даёт права менять выбор аккаунта.

Nullable avatar/alias/description/icon в Go-моделях представлены `*string`:
NULL и пустая строка сохраняют разные значения. `users.role_id` (SMALLINT) соответствует `int16`.

После входа открывается `/characters` со списком персонажей, либо `/game`, если персонаж
уже выбран. `/characters/new` создаёт персонажа с именем, фракцией и классом из справочника.
При смене фракции выбор класса сбрасывается; список содержит только совместимые классы.
Создание возвращает к списку. Вход за персонажа выполняется отдельно кнопкой «Играть».
На экране персонажа кнопка «К выбору персонажа» явно сбрасывает общий выбор аккаунта.
Обычные переходы и GET-запросы выбор не меняют.

Имя содержит 3–32 символа: латинские/кириллические буквы, пробел, дефис, ASCII-апостроф;
начинается и заканчивается буквой. Убираются пробелы по краям, повторные обычные пробелы
сжимаются, Unicode приводится к NFC. Имена уникальны без учёта регистра во всей игре.
Миграция `20261025000400_character_names` закрепляет нормализованный уникальный ключ в БД.
Для кириллицы и латиницы используется отдельная ICU collation `character_name_unicode`,
поэтому правило не зависит от системной локали базы. При конфликтующих старых именах
миграция прерывается целиком, не переименовывая и не удаляя персонажей. Down сохраняет
данные и возвращает прежнее ограничение уникальности с учётом регистра.
Минимальная версия PostgreSQL повышена с 12 до 14 из-за SQL-функции с разобранным телом
`RETURN` и поддержкой Unicode-нормализации; [описание SQL-функций](https://www.postgresql.org/docs/14/sql-createfunction.html)
и [ICU collation](https://www.postgresql.org/docs/14/collation.html).

Новый персонаж получает SQL-значения по умолчанию (уровень 1, роль `dd`, начальные
характеристики) и способности своего класса в одной транзакции. Создание и выбор сначала
блокируют аккаунт, затем заново проверяют сессию: запрос, ожидавший завершения logout,
не может восстановить выбор с отозванной сессией.

Frontend хранит состояние аккаунта централизованно. Выбор с другого устройства обновляется
при возвращении во вкладку и каждые 15 секунд в видимой вкладке. Перекрывающиеся обновления
объединяются; запоздавшие ответы не отменяют новый вход, выход или локальный выбор.
На `/game` пока отображаются имя, уровень, опыт и HP/MP; боевые механики — отдельный этап.

### Ограничения игровых данных

Миграция `20261025000700_character_stats_integrity` закрепляет правила в PostgreSQL:

| Поле | Правило |
| --- | --- |
| class_id + role | Связка должна существовать в class_roles |
| level | Уровень должен существовать в levels |
| experience | Неотрицательное число |
| hp, hp_current | hp > 0; текущее здоровье от 0 до hp включительно |
| mp, mp_current | mp >= 0; текущий ресурс от 0 до mp включительно |
| mastery, endurance, power, accuracy, alacrity, critical, defense, shield, absorption | Неотрицательные значения |
| levels.level, levels.experience_required | Положительный номер уровня и неотрицательный порог опыта |

Нулевое текущее HP допустимо; персонаж без MP хранит mp=mp_current=0. При уменьшении
максимума ниже текущего значения оба поля нужно изменять одним UPDATE. Характеристики
хранят числовые значения без искусственного потолка 100; верхняя граница задаётся типом
INTEGER. Максимальный уровень определяется справочником: расширение за текущие 50
уровней не требует изменения ограничения. Начислением опыта и повышением уровня
управляет серверный сервис progression, описанный ниже.

Роль проверяется также при смене класса. Удалить или изменить используемую запись
class_roles/levels нельзя, пока на неё ссылаются персонажи. Индексы
characters_class_role_idx и characters_level_idx поддерживают эти внешние ключи.
Справочники должны быть заполнены перед созданием персонажей: SQL defaults остаются
`role='dd'`, `level=1`, `experience=0`, HP/MP=100. Отсутствие нужной строки справочника
прерывает создание целиком и считается внутренней ошибкой конфигурации данных.

Up-миграция блокирует characters, class_roles и levels, проверяет старые строки и
добавляет все ограничения одной транзакцией. При нарушении выдаётся категория ошибки
`character stats:`; исправьте справочник или данные осознанно и повторите миграцию.
Автоматического исправления значений нет. Down удаляет добавленные ограничения и
два индекса, сохраняя данные, defaults и прежние правила владения/класса/фракции.

### Опыт и повышение уровня

`characters.experience` — общий накопленный опыт; `levels.experience_required` —
общий порог достижения указанного уровня. Например, при порогах 0 / 100 / 250
переход со второго на третий требует ещё 150 опыта. Опыт при повышении не обнуляется,
одна награда может повысить сразу несколько уровней.

`internal/progression` содержит чистый расчёт `Curve` и сервис `Service`;
`db.ProgressionRepository` сохраняет результат. Пороги и максимальный уровень
читаются из levels при каждом новом начислении. Числа баланса в Go не зашиты:
каталог должен начинаться с уровня 1 и порога 0, идти без пропусков, с возрастающими
порогами. Некорректный каталог отклоняет новое начисление без частичной записи.

При достижении максимального уровня сохраняется только опыт до его порога;
избыток отбрасывается. На максимуме последующие награды дают 0 XP. Изменение порогов
не отнимает уже заработанные опыт и уровень: новый порог влияет на последующие
начисления. Повышение порога существующего максимального уровня не включает набор
опыта снова; добавление нового уровня позволяет получать новые награды.
Массовый пересчёт существующих персонажей при балансировке требует отдельной операции.
Повышение уровня пока не меняет характеристики и не восстанавливает HP/MP.

Начисление — внутренний серверный вызов для будущих боёв/заданий. Вызывающий код
сначала проверяет право персонажа на награду и сам определяет сумму и ключ события:

~~~go
xp := progression.NewService(db.NewProgressionRepository(pool))
result, err := xp.Grant(ctx, progression.Reward{
    CharacterID: characterID,
    Key:         "quest:123/attempt:7",
    Experience:  150,
})
~~~

Ключ уникален для персонажа: 1–128 ASCII-символов, первый — буква/цифра,
остальные — буквы, цифры или `:._/-`. Сумма — положительное int64. Повтор с тем же
ключом и суммой возвращает **исходный** результат с `Replayed=true`, без нового
начисления; другая сумма для использованного ключа — `ErrRewardConflict`.
`Change.Granted` показывает фактически выданный опыт, `Before`/`After` — состояние
при исходной операции. Для актуального состояния после других наград нужно перечитать
персонажа. Клиентского маршрута с произвольной суммой опыта нет; существующий API
персонажей уже возвращает уровень и общий опыт.

Миграция `20261025000800_experience_rewards` добавляет журнал
`character_experience_rewards`. Блокировка строки персонажа, обновление level/experience
и запись события выполняются одной транзакцией: параллельные награды не теряются,
повтор одного события не удваивает XP. Записываются даже нулевые начисления на максимуме,
чтобы после добавления уровней старые события не превратились в запас опыта.
Журнал хранится до удаления персонажа, без очистки по возрасту. Down допускается
только для пустого журнала; при наличии наград он останавливается, сохраняя защиту
от повторов. Для такого отката сначала нужен отдельный план сохранения истории.

### API персонажей

Все маршруты требуют действующей сессии. `user_id`, роль, уровень и характеристики
не принимаются от клиента. Входные JSON-объекты проверяются строго.

| Метод и маршрут | Вход | Успех |
| --- | --- | --- |
| GET /api/characters/catalog | Cookie | 200: factions, classes |
| GET /api/characters | Cookie | 200: characters, active_character_id |
| POST /api/characters | name, faction_id, class_id | 201: character |
| PUT /api/characters/active | character_id: число или null | 200: character или null |

Пустой объект при выборе — ошибка: для сброса требуется явное `{"character_id":null}`.
404 одинаков для чужого и несуществующего персонажа; 409 — занятое имя;
422 — недопустимое имя, ID или сочетание класса и фракции. Остальные HTTP-правила
совпадают с авторизацией: 401, JSON-ошибки, лимит тела, запрет чужого origin и no-store.

~~~dotenv
APP_ENV=production
~~~

Повторная отправка заменяет прежнюю ссылку. Если она не удалась, повторите ещё раз.
Фоновой очереди и автоматических повторов пока нет.

### IP клиента за reverse proxy

Без `TRUSTED_PROXIES` лимитер использует IP соединения (`RemoteAddr`) и игнорирует
заголовки прокси. Loopback и приватные сети автоматически доверенными не становятся.
Для локального прокси можно явно указать `TRUSTED_PROXIES=127.0.0.1/32,::1/128`;
для отдельного сервера — его точный IP или необходимую подсеть. Поддерживаются IPv4,
IPv6 и CIDR через запятую; имена хостов, порты и zone identifiers не принимаются.
Неверная настройка останавливает запуск; её значение в диагностике не выводится.

Только если непосредственный peer доверенный, сервер читает `X-Forwarded-For`
справа налево: пропускает доверенные прокси и останавливается на первом недоверенном
адресе. Всё слева от него игнорируется, включая подставленные клиентом IP.
Повторяющиеся поля заголовка обрабатываются как одна цепочка в порядке получения.
Если вся цепочка доверенная, выбирается её крайний левый адрес.

Прокси должен перезаписывать входящий `X-Forwarded-For` фактическим IP клиента
или дописывать к цепочке адрес своего соединения с клиентом. Не включайте клиентские
сети в доверенные: список обозначает именно узлы, которым разрешено сообщать чужой IP.
В цепочке из нескольких прокси настройте доверие для всех её управляемых узлов.
Если прокси без проверки передаёт заголовок клиента, приложение не сможет отличить подмену.

Пустой/некорректный проверяемый суффикс возвращает лимитер к IP соединения.
Общий размер значений заголовка с разделителями ограничен 4096 байтами;
проверяется максимум 32 адреса справа. Превышение также возвращает IP соединения:
такие запросы за одним прокси делят общий лимит. В заголовке допустимы только IP
без портов, скобок или зон. Эквивалентные IPv6 и IPv4-mapped адреса получают один ключ;
IPv4-mapped CIDR разрешён с длиной от /96 и нормализуется в IPv4. Обычный IPv6 CIDR
не задаёт доверия для IPv4.

`Forwarded`, `X-Real-IP`, `X-Forwarded-Proto` и `X-Forwarded-Host` не используются.
Настройка определяет только IP для лимитера; доверенный origin и Secure cookie
по-прежнему определяет `PUBLIC_URL`. Лимит хранится в памяти каждого процесса:
для нескольких экземпляров приложения потребуется общий лимитер или ограничение на прокси.

### Даты и метаданные записей

Все колонки дат событий используют `timestamptz`: created_at/updated_at,
подтверждение email, активация персонажа, даты наград и сроки действия сессий/токенов.
Они хранят момент времени; часовой пояс соединения влияет на его текстовое
представление, а не на срок действия. В Go сравнивайте моменты через `time.Time.Equal`.

При INSERT created_at и updated_at по умолчанию равны `NOW()` — началу транзакции.
При UPDATE общая функция `set_row_updated_at` обновляет updated_at временем
PostgreSQL (`clock_timestamp()`) только при изменении строки. Запись тех же значений
оставляет дату прежней; изменение одного updated_at считается явным обновлением,
но переданное значение заменяется текущим временем БД. created_at триггер не меняет.
Правило действует для users, sessions, email_verifications, factions, classes,
abilities и characters, включая прямой SQL. Метаданные откатываются вместе со строкой.
Репозитории не присваивают updated_at; новые таблицы с этим полем должны подключать
такой же триггер в своей миграции. Событийные даты вроде email_verified_at остаются
отдельными значениями и могут отличаться от времени изменения записи.

Миграция `20261025000600_timestamp_consistency` выполняется транзакционно.
Запускайте её при остановленном API: изменение типов блокирует таблицы, старые
соединения могут держать подготовленные запросы с прежними типами результатов.
Для старых created_at/updated_at/activated_at используется `TimeZone` соединения
миграции — та зона, в которой прежняя БД записывала NOW()/clock_timestamp().
Смена этой настройки перед миграцией без пересчёта данных сдвинет их смысл.

У прежнего кода подтверждения был отдельный путь: email_verified_at и updated_at
записывались одним значением UTC. Поэтому email_verified_at интерпретируется в UTC,
а users.updated_at — в UTC, когда он равен email_verified_at; иначе действует зона
метаданных. Это правило описывает записи текущего приложения. У импортированных
или вручную заданных дат нужно заранее проверить источник зоны и совпадения полей:
timestamp без зоны сам по себе не содержит информации для её восстановления.
В существующие абсолютные expires_at/expired_at миграция не вмешивается.

Откат снимает триггеры и возвращает прежние типы/правила, сохраняя строки и NULL.
Для up/down используйте одну исходную `TimeZone`; откат к timestamp снова теряет
явную привязку к моменту времени (в том числе неоднозначен при переходах летнего времени).
Перед возвратом старого приложения требуется соответствующая версия репозиториев,
которая сама обновляла updated_at.

## API авторизации

Все тела запросов, кроме пустого logout, — JSON; максимальный размер 16 KiB.
Ответы API не кэшируются. Данные пользователя в ответе: id, email, login, character_id (число или null).

| Метод и маршрут | Вход | Успех |
| --- | --- | --- |
| POST /api/auth/register | email, login, password | 201: message, verification_sent |
| POST /api/auth/login | email, password | 200: user; Set-Cookie |
| GET /api/auth/me | Cookie | 200: user |
| POST /api/auth/logout | Cookie, необязательная | 200: message; удаление cookie |
| POST /api/auth/verify | token | 200: message |
| POST /api/auth/resend-verification | email, password | 200: message |

Для совместимости verify также принимает token в query при пустом теле POST.
GET /verify?token=... открывает страницу и сам по себе не подтверждает email.
Logout идемпотентен, в том числе без cookie. Ошибка удаления сессии из БД возвращает 500;
cookie при этом сохраняется, чтобы можно было повторить выход.

Email нормализуется trim + lowercase; login trim, 1–32 символа; новый пароль 8–72 байта.
Вход со старыми короткими паролями сохранён.

Регистрация, вход, подтверждение и resend имеют общий лимит 30 запросов в минуту на IP.
IP берётся из RemoteAddr либо из цепочки X-Forwarded-For согласно TRUSTED_PROXIES
(см. «IP клиента за reverse proxy»). Защита от cross-origin работает независимо от лимита.
Строки истёкших сессий больше не аутентифицируют; их очистка доступна через `npm run cleanup`.

## Ошибки HTTP API

Все ошибки `/api/*`, включая отказы middleware и неизвестные маршруты, используют
один JSON-формат и `Cache-Control: no-store`:

~~~json
{
  "error": "Проверьте заполненные поля",
  "code": "validation_failed",
  "fields": {"password": ["Пароль должен содержать от 8 до 72 байт"]},
  "errors": ["Пароль должен содержать от 8 до 72 байт"]
}
~~~

`error` — сообщение для человека, `code` — стабильный код для логики клиента.
Оба поля обязательны. Необязательный `fields` связывает JSON-имена полей запроса
с массивами сообщений. Для прежних клиентов сохранён `errors`: он автоматически
собирается из `fields` в порядке отсортированных ключей. Без ошибок полей эти два
необязательных поля отсутствуют. Внутренние SQL-ошибки и секреты в ответ не попадают.

| HTTP | code | Значение |
| --- | --- | --- |
| 400 | invalid_json | Некорректный JSON, лишнее поле, не объект или несколько значений |
| 400 | invalid_request | Отсутствующий или неверного типа character_id; ошибка поля character_id |
| 400 | verification_token_invalid | Недействительная или истёкшая ссылка подтверждения |
| 401 | unauthenticated | Нет действующей сессии |
| 401 | invalid_credentials | Неверный email или пароль |
| 403 | email_unverified | Для входа нужно подтвердить email |
| 403 | origin_forbidden | Запрос отклонён защитой от чужого origin |
| 404 | route_not_found | Неизвестный API-маршрут |
| 404 | character_not_found | Персонаж отсутствует или принадлежит другому аккаунту |
| 405 | method_not_allowed | Метод не поддерживается; допустимые методы в Allow |
| 409 | account_conflict | Email или логин занят |
| 409 | email_already_verified | Email уже подтверждён |
| 409 | character_name_taken | Имя персонажа занято; ошибка поля name |
| 413 | request_too_large | Тело больше 16 KiB |
| 415 | unsupported_media_type | Требуется Content-Type: application/json |
| 422 | validation_failed | Неверные значения; подробности по полям в fields |
| 422 | character_class_mismatch | Класс несовместим с фракцией; ошибка поля class_id |
| 429 | rate_limited | Частые запросы; задержка повтора в Retry-After |
| 500 | internal_error | Внутренняя ошибка без технических подробностей |
| 503 | mail_delivery_failed | Не удалось повторно отправить письмо |

Регистрация с неудачной отправкой письма остаётся успешным созданием аккаунта:
`201` и `verification_sent: false`. Повторная регистрация для восстановления доставки не нужна.

Frontend показывает ошибки регистрации и создания персонажа рядом с соответствующими
полями и убирает их при редактировании. Подсказка о подтверждении почты появляется только
для `403/email_unverified`. `401/unauthenticated` завершает локальное состояние сессии,
а `401/invalid_credentials` не сбрасывает уже действующий аккаунт. Для старых ответов
без code/fields сохраняются общие сообщения и прежняя обработка 401.

- расширяет email до 254 символов и добавляет уникальность нормализованного адреса;
- переводит срок подтверждения в timestamptz и добавляет expires_at сессий;
- хеширует существующие токены, сохраняя возможность использовать исходные ссылки/cookie;
- ограничивает старые сессии сроком created_at + 168 часов.

Для старых timestamp используется TimeZone сессии миграции: задайте ту же зону,
в которой создавались прежние строки. Совпадения адресов после trim/lower останавливают
миграцию целиком, без удаления аккаунтов. Предварительная проверка:

~~~sql
SELECT lower(btrim(email)), count(*)
FROM users
GROUP BY lower(btrim(email))
HAVING count(*) > 1;
~~~

Down-миграция отзывает сессии и ссылки: исходные токены невозможно восстановить из хешей.
Если уже есть email длиннее 32 символов, rollback останавливается, чтобы не усечь данные.
Миграция использует встроенную функцию [sha256 PostgreSQL](https://www.postgresql.org/docs/12/functions-binarystring.html).

## Архитектура и тесты

- internal/auth — правила, пароль, токены, сроки, безопасная Identity и интерфейсы.
- internal/character — правила имён, создание и выбор персонажей, контракт репозитория.
- internal/db — отдельные AuthRepository и CharacterRepository с общим пулом PostgreSQL.
- internal/mailer — общие письма и драйверы доставки.
- internal/validation — ошибки полей без зависимости от HTTP.
- internal/httpapi — общий формат JSON-ответов и строгое чтение тела запроса.
- internal/observability — request ID/логгер в контексте и безопасные категории ошибок.
- internal/handlers, middleware, routes — преобразование доменных ошибок в HTTP, cookie,
  маршруты и защита запросов.
- cmd/app — сборка зависимостей, серверные таймауты и graceful shutdown.
- cmd/seed и internal/seed — отдельная команда справочников и транзакционное выполнение SQL.
- cmd/cleanup и internal/maintenance — отдельная команда обслуживания истёкших сессий/email-токенов.
- frontend/src/account — общее состояние аккаунта и защита от устаревших ответов API.
- frontend/src/pages/characters — список, создание и экран выбранного персонажа.

Интерфейс целиком находится во frontend: Go отдаёт собранную SPA из frontend/dist.
Состояние аккаунта подключается к React через Context и useSyncExternalStore.

Реквизиты входа отделены от данных текущего аккаунта. `auth.Credentials` содержит
хеш пароля и загружается только для проверки пароля при login/resend. `auth.Identity`
содержит ID аккаунта, роль, nullable ID персонажа, email, логин и отметку подтверждения email.
Именно Identity возвращается из авторизации и передаётся в HTTP-контекст; запрос сессии
не читает пароль, профиль или даты создания/обновления аккаунта. Ответ API строится
отдельным DTO с четырьмя публичными полями, перечисленными выше.

Запись регистрации передаётся в репозиторий структурой `auth.Registration`
с именованными полями и готовыми хешами. Аккаунт и подтверждение по-прежнему сохраняются
одной транзакцией; общий тип SQL-модели User не используется в контрактах авторизации.

Все тесты находятся отдельно от кода приложения:

~~~text
tests/
  app/        # запуск API-процесса и безопасные структурированные ошибки конфигурации
  auth/       # сценарии авторизации
  character/  # правила имени и входные данные персонажей
  config/     # загрузка и проверка настроек
  db/         # контракт хранилища и интеграция с PostgreSQL
  devtools/   # запуск команд, обязательные настройки, обработка сбоев и секретов
  httpapi/    # JSON-контракт, декодирование, лимит тела и ошибки сериализации
  mailer/     # local и SMTP, тестовые сертификаты
  middleware/ # request ID, учёт ответа, потоковая отправка и обработка паник
  progression/ # накопительный опыт, пороги, максимум, балансировка и входные награды
  routes/     # HTTP API, cookie, защита запросов и SPA
  seed/       # запуск CLI сидов и миграции справочников на PostgreSQL
  testenv/    # требования к окружению интеграционных тестов
  frontend/   # ошибки API, состояние аккаунта и browser smoke test
~~~

Go-тесты импортируют публичные интерфейсы из internal/. Для проверки времени используется
виртуальное время testing/synctest; SMTP-сертификаты доверенные только внутри процесса тестов.
Установка сертификатов в ОС и доступ к закрытым полям приложения не требуются.

~~~powershell
npm test
npm run lint
npm run build
~~~

Из корня можно запустить только Go-тесты: `go test ./tests/...`.
Для отчёта о покрытии кода приложения используйте
`go test -coverpkg=./internal/... ./tests/...`: сами каталоги tests содержат только проверки.

Для проверки SQL укажите отдельную тестовую БД:

~~~powershell
$env:TEST_DATABASE_URL = 'postgres://user:password@localhost:5432/gotest_test?sslmode=disable'
go test -count=1 -v ./tests/db ./tests/seed
~~~

Тесты SQL не используют DATABASE_URL приложения. Каждый создаёт случайную отдельную схему,
применяет миграции и удаляет свою схему после завершения; учётной записи нужны соответствующие права.
Без TEST_DATABASE_URL локально эти тесты явно пропускаются; в CI или обязательном режиме
это ошибка. SMTP-тесты используют только локальный
тестовый сервер с тестовыми сертификатами и не отправляют настоящую почту.

Тесты seed собирают настоящую CLI-команду, запускают её в отдельных временных папках
и проверяют повторный/параллельный запуск, смещённые ID, сохранение настроенного баланса,
откат при ошибке и таймауте, независимость от HTTP/SMTP и миграцию существующих данных.

Для браузерной проверки соберите frontend, задайте TEST_DATABASE_URL как выше и путь
к Chrome/Chromium/Edge. Проект использует Node.js 24+ с встроенным WebSocket:

~~~powershell
$env:CHARACTER_BROWSER_BINARY = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
go test -count=1 -run TestCharacterBrowserFlow -v ./tests/db
~~~

Тест открывает временный HTTP-сервер и отдельный headless-профиль браузера, проверяет
ошибки полей и их сброс при редактировании, разные причины 403, создание и фильтрацию
классов, конфликт имени, выбор после перезагрузки и два независимых сеанса.
Используется временная SQL-схема; обычные аккаунты и профиль браузера не затрагиваются.
Без CHARACTER_BROWSER_BINARY браузерный тест локально пропускается, а в CI/обязательном
режиме завершается ошибкой. Для сохранения снимков можно задать CHARACTER_SCREENSHOT_DIR
внутри `.local/`: npm-команды разрешают относительный путь от корня проекта;
для прямого go test используйте абсолютный путь. `npm run check` сам собирает frontend
перед браузерной проверкой.
