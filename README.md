# Go Test

Go API + PostgreSQL + React SPA. Авторизация использует серверные сессии в HttpOnly cookie.
Токены сессий, подтверждения email и сброса пароля проверяются по SHA-256; пароли — bcrypt.
До отправки писем их содержимое хранится в зашифрованной PostgreSQL-очереди.

Чат обновляется через WebSocket, хранит историю в PostgreSQL и поддерживает модерацию.
Роли `user`, `moderator`, `administrator` и ограничения относятся к аккаунту.
Модераторы удаляют сообщения и управляют временными банами чата/форума; администратор
также блокирует аккаунты. Форум `/forum` поддерживает разделы, темы, ответы,
редактирование своих публикаций и модерацию. Авторы — выбранные персонажи;
состояние блокировок общее для всех персонажей аккаунта. Административная панель
пока не реализована.
Назначение роли через локальную команду описано в [operations.md](docs/operations.md#роли-и-модерация).

Список «Кто онлайн» доступен по `/online` и из футера. Онлайн относится к выбранному
персонажу и действует 120 секунд после подтверждённого действия игрока. Автоматические
обновления страниц не продлевают статус; несколько вкладок и сессий не увеличивают
счётчик. Сигналы активности объединяются в пределах 15 секунд, индикаторы и список
обновляются каждые 30 секунд и при возвращении во вкладку. Состояние хранится в
сессиях PostgreSQL; отдельный процесс очистки присутствия не требуется.

ХП восстанавливаются от нуля до максимума за 5 минут, энергия — за минуту.
Восстановление идёт постоянно, включая бой и отсутствие игрока в сети, до заполнения
соответствующего ресурса. База хранит опорный остаток и время, Go рассчитывает актуальное
значение, а браузер обновляет отображение между серверными ответами.

Доступен PvE-бой один на один с общим экземпляром NPC в текущей локации.
Игрок применяет изученные умения с личными кулдаунами и GCD; NPC действует
по серверному таймеру. Победа выдаёт опыт и кредиты один раз, отступление
восстанавливает NPC. Экран боя, журнал и переиспользуемая панель умений описаны
в разделе [«Экран боя»](#экран-боя). Галактическая война, лут и расширение
наборов умений остаются отдельными этапами.

## Запуск

Нужны Go 1.26.10+, Node.js 24+ с npm, PostgreSQL 14+ с ICU и базой в UTF8,
а также CLI golang-migrate для SQL-миграций. Локальные проверки выполнены на PostgreSQL 18.3.
Команды npm выполняются из корня проекта, кроме отмеченных команд frontend.
Для собранного API можно явно выбрать конфигурацию и запускаться из любой папки.

1. При первом запуске создайте .env по .env.example; существующий .env дополните новыми параметрами.
2. Укажите DATABASE_URL и MAIL_QUEUE_KEY (см. раздел «Почтовая очередь»).
   Для обычного запуска PUBLIC_URL=http://localhost:8081.
3. Установите зависимости и примените миграции к выбранной БД:

~~~powershell
npm run setup
npm run migrate
~~~

Команда npm run migrate загружает `.env` и вызывает установленный CLI `migrate` из PATH.
Значения окружения имеют приоритет; `npm run migrate -- version` показывает текущую версию.
Для локальной PostgreSQL без TLS укажите в URL параметр `sslmode=disable`:
`?sslmode=disable` либо `&sslmode=disable`, если другие параметры уже есть.
Приложение намеренно не запускает миграции при старте.

4. Загрузите справочники, соберите приложение и запустите API:

~~~powershell
npm run seed
npm run build
npm run dev:api
~~~

Откройте http://localhost:8081/register. В режиме local письмо появится в .local/mail.
Для копирования ссылки из редактора откройте соответствующий `.txt` и перейдите
по ссылке: адрес подтвердится автоматически. `.eml` предназначен для почтового клиента: в его исходном
тексте ссылка MIME-кодирована и может быть перенесена на несколько строк.
После этого доступны вход, создание и выбор персонажа.

Для Vite dev задайте PUBLIC_URL=http://localhost:5173, запустите npm run dev:api и отдельно
npm run dev:web из корня проекта. Запросы /api проксируются на localhost:8081; при смене APP_PORT
обновите адрес proxy в frontend/vite.config.ts.

Общие элементы интерфейса и палитра находятся в
[shared/ui/kit](frontend/src/shared/ui/kit/README.md). При запуске Vite страница
`http://localhost:5173/_ui-kit` показывает компоненты и их состояния; в production
эта галерея не включается в сборку.

### Конфигурация и запуск из другой папки

API принимает `-env-file`: путь к dotenv-файлу может быть абсолютным или относительно
папки запуска. Например, после сборки эти команды работают из любой рабочей папки:

~~~powershell
& 'C:/games/gotest/.local/bin/app.exe' -env-file 'C:/games/gotest/.env'
~~~

~~~sh
/srv/gotest/.local/bin/app -env-file /srv/gotest/.env
~~~

`STATIC_DIR` задаёт каталог собранной SPA (по умолчанию `frontend/dist`), `MAIL_DIR` —
каталог писем local-драйвера (по умолчанию `.local/mail`). Относительные пути обоих
параметров, включая значения из окружения, считаются **от папки загруженного dotenv-файла**.
Абсолютные пути используются напрямую. Если файл лежит в `config/app.env`, путь
`STATIC_DIR=../frontend/dist` указывает на frontend рядом с папкой config.

Без флага API пробует `.env` в рабочей папке; отсутствие этого неявного файла допустимо.
Явно переданный файл обязателен. Ошибка чтения или синтаксиса существующего файла
останавливает запуск с безопасной диагностикой. `-env-file=` отключает чтение файлов
и использует только окружение. Когда файл не загружен, относительные пути считаются
от рабочей папки запуска. Папка самого бинарника базой путей не является.

Переменные процесса имеют приоритет над файлом, в том числе явно пустые значения;
для пустых значений сохраняются предусмотренные настройкой defaults. Загрузка файла
не меняет окружение процесса, пути преобразуются в абсолютные один раз при старте.
Для сервиса с конфигурацией только через окружение удобно задать абсолютные STATIC_DIR
и MAIL_DIR и запустить бинарник с `-env-file=`. Справка `-help` работает без БД и конфигурации.

В `APP_ENV=production` STATIC_DIR должен содержать доступный непустой файл index.html:
ошибка останавливает запуск до открытия HTTP-порта. В local/staging отсутствие сборки
допустимо: API и health endpoints работают, а запросы отсутствующей SPA получают 404.
Это позволяет запускать Vite отдельно. Маршруты `/api` и отсутствующие ассеты сохраняют
свои ответы и не подменяются index.html.

Для запуска через Go доступно `npm run dev:api -- -env-file ./config/app.env`.
CLI `seed` и `cleanup` по-прежнему ищут `.env` в своей рабочей папке; при запуске из
другого места передайте DATABASE_URL через окружение, а seed также укажите `-dir`.
Команды npm устанавливают рабочую папку дочерних процессов в корень проекта.

## Команды разработки и CI

Команды из корня одинаковы для PowerShell и Linux. В корневом package.json находятся
инструменты генерации API; зависимости приложения и сборки frontend — в frontend/package.json.

| Команда | Что выполняется |
| --- | --- |
| npm run setup | go mod download и npm ci в корне и frontend по двум lock-файлам |
| npm run dev:api | Go API; можно передать `-- -env-file ./config/app.env` |
| npm run dev:web | Vite; запускается в отдельном терминале |
| npm run build | Go-бинарники в .local/bin и frontend/dist |
| npm run lint | Проверка gofmt, go vet и frontend ESLint |
| npm run audit | Проверка npm-зависимостей приложения и сборки; нужен доступ к npm Registry |
| npm run audit:go | govulncheck v1.9.0 для Go-кода и тестов; нужна сеть для базы уязвимостей |
| npm run api:generate | Генерация TypeScript-типов из api/openapi.yaml |
| npm run api:check | Актуальность типов, проверки TypeScript и HTTP-контракта; БД и браузер не нужны |
| npm run migrate | Применение up-миграций; `-- version` показывает версию |
| npm run seed | Транзакционные сиды; можно передать `-- -dir ./seeds -timeout 30s` |
| npm run cleanup | Очистка истёкших сессий, токенов и почты; `-- -battle-logs` добавляет старые боевые журналы, `-- -dry-run` только считает |
| npm run mail:status | Счётчики почтовой очереди без содержимого писем; `-- -timeout 10s` |
| npm run db:backup | Новая резервная копия БД; `-- -dir .local/backups/unique-name` |
| npm run db:restore | Восстановление копии в отдельную пустую RESTORE_DATABASE_URL; `-- -dir .local/backups/unique-name` |
| npm test | Тесты команд, Go и frontend; локально допускает ненастроенные интеграционные проверки |
| npm run test:integration | SQL-тесты db/seed; TEST_DATABASE_URL обязателен |
| npm run test:race | Go race detector и SQL-тесты; требует C-компилятор и TEST_DATABASE_URL |
| npm run test:combat-load | Отдельные нагрузочные сценарии боёв на тестовой БД; браузер не требуется |
| npm run check | Актуальность API-типов, lint, обе сборки и все тесты; БД и браузер обязательны |
| npm run test:db:up | Отдельная тестовая PostgreSQL через Docker Compose с ожиданием готовности |
| npm run test:db:down | Удаление только Compose-окружения тестовой БД и его данных |

Go-команды ограничены каталогами cmd/internal/tests: Go-файлы из node_modules не участвуют
в проверках. Для Go-исходников `.gitattributes` закрепляет LF, чтобы gofmt одинаково
работал после checkout на Windows и Linux. LF также закреплён для генерируемого schema.d.ts:
проверка генератора сравнивает содержимое побайтно. Любая ошибка команды останавливает общий запуск.

Для полного локального прогона скопируйте `.env.test.example` в `.env.test` (если файла
ещё нет) и укажите абсолютный путь CHARACTER_BROWSER_BINARY к Chrome/Chromium/Edge.
Например: `C:/Program Files/Google/Chrome/Application/chrome.exe` или `/usr/bin/google-chrome`.
Файл `.env.test` исключён из Git; переменные терминала имеют приоритет над его значениями.
Тестовые команды загружают только этот файл, без подстановки DATABASE_URL из `.env`.
Полный прогон также требует `pg_dump`/`pg_restore` версии сервера: задайте POSTGRES_BIN_DIR
или добавьте их в PATH. Роль TEST_DATABASE_URL должна иметь CREATEDB: тест восстановления
создаёт и удаляет только собственные случайно названные базы, отдельно от приложения.

Если используете Docker Desktop/Engine с Linux-контейнерами:

~~~powershell
npm run test:db:up
npm run check
npm run test:db:down
~~~

Compose поднимает PostgreSQL 18.6-bookworm с ICU и UTF8 на `127.0.0.1:55432`;
адрес и тестовые реквизиты есть в `.env.test.example`. Данные временные, в tmpfs,
и не связаны с БД приложения. Для PostgreSQL 18 используется точка монтирования
`/var/lib/postgresql`, согласно [документации официального образа](https://github.com/docker-library/docs/blob/master/postgres/README.md#pgdata).
Можно использовать отдельно установленную тестовую PostgreSQL: задайте её адрес
в TEST_DATABASE_URL, и команды Docker не понадобятся. Если переключаетесь на Compose,
убедитесь, что TEST_DATABASE_URL указывает на порт 55432 из примера.

При `CI=true`/`CI=1` даже прямой `go test` завершится ошибкой, если обязательные
TEST_DATABASE_URL или CHARACTER_BROWSER_BINARY отсутствуют. Вне CI такое поведение можно
включить отдельно через REQUIRE_DATABASE_TESTS=1 и REQUIRE_BROWSER_TESTS=1.
`npm run check` включает оба требования автоматически; ошибка соединения, запуска браузера
или отсутствие собранного frontend также приводят к ошибке, а не пропуску.

`.github/workflows/ci.yml` запускается для PR, push в master и вручную. Он использует
Ubuntu 24.04, Go из go.mod, Node из .node-version, отдельный PostgreSQL service с healthcheck
и установленный Chrome. Устанавливаются клиентские инструменты PostgreSQL 18; после setup
выполняются audit, audit:go, та же команда check и test:race. Порт PostgreSQL
выбирается runner автоматически и передаётся в шаг проверки по
[контракту service containers GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).
Actions закреплены по SHA, права ограничены чтением репозитория; секреты и деплой не нужны.

`test:race` включает CGO и проверяет все Go-пакеты тестов, включая PostgreSQL и восстановление
резервной копии. Браузерные `TestCharacterBrowserFlow`, `TestSocialBrowserFlow` и
`TestForumBrowserFlow` исключены из этого повторного прогона: они обязательны в `check`.
На Linux нужен GCC/Clang, на Windows — совместимый с Go
C-компилятор в PATH. Обычный `check` не требует C-компилятора. Ошибки race detector и
govulncheck завершают CI с ненулевым кодом; найденные уязвимости не подавляются.

## Контракт HTTP API

[`api/openapi.yaml`](api/openapi.yaml) описывает существующие операции auth/character,
health/readiness, тела запросов и ответов, ошибки, заголовки и cookie сессии в OpenAPI 3.0.3.
Это источник публичных TypeScript-контрактов. Go DTO остаются в модулях, которым принадлежат;
соответствие их HTTP-представления схеме проверяется тестами.

[`openapi-typescript`](https://openapi-ts.dev/cli) генерирует
`frontend/src/shared/api/schema.d.ts`. Файл хранится в Git и не редактируется вручную.
Типы entities ссылаются на schemas из этого файла; shared/api/client связывает URL и метод
с входными данными и успешным ответом. Axios сохраняет отправку cookies, ошибки и отмену
запросов. Строгий режим TypeScript сохраняет различие между null, отсутствующим полем и значением.

При изменении API обновите схему, обработчик и сценарии в tests/routes/openapi_test.go,
затем выполните из корня:

~~~powershell
npm run api:generate
npm run api:check
~~~

Проверка не переписывает артефакт: устаревшие типы завершают её с ошибкой. Схему и результат
генерации коммитьте вместе. `npm run check` включает эту проверку и весь набор контрактных
тестов; `npm test` во frontend также компилирует негативные type-тесты из tests/frontend.
Генератор использует собственный TypeScript 5 в корневых devDependencies из-за своего
peer-ограничения; frontend продолжает использовать TypeScript 6. Обе версии закреплены lock-файлами.

Go-тесты используют [`kin-openapi`](https://github.com/getkin/kin-openapi) только при тестировании:
настоящий роутер, middleware и handlers, сервисы с контролируемыми результатами. Проверяются
запросы, статусы, JSON и заголовки ответов, nullable-поля, cookies, ошибки и HEAD без тела.
Для каждой описанной операции требуется успешный HTTP-сценарий; Allow сверяется со схемой.
Новый маршрут нужно добавить и в схему, и в сценарии. Проверки с PostgreSQL и браузером
отдельно подтверждают работу сервисов и пользовательских сценариев. В production нет
дополнительной OpenAPI-валидации каждого запроса.

Не все правила выражаются JSON Schema: пароль ограничен 8–72 байтами UTF-8, email —
254 байтами после нормализации, имя персонажа проверяется после NFC/trim. Эти правила
описаны в схеме и проверяются доменными тестами. Legacy query-token у verify поддерживается
только без тела; frontend отправляет token в JSON.
Защищённые операции принимают `X-Account-ID` как ожидаемый ID владельца cookie. Авторизация
по-прежнему определяется серверной сессией; несовпадение даёт `409/account_changed` до
изменения данных или cookie. Штатный frontend всегда передаёт этот ID, а `/me` получает
без него для определения текущего аккаунта. У старых клиентов заголовок необязателен.

Вход, выход и сброс пароля синхронизируются между вкладками через BroadcastChannel или
storage events без передачи секретов. При смене аккаунта старые запросы отменяются,
локальные формы очищаются, данные перечитываются. Клиент ограничивает каждый запрос
20 секундами. Таймаут не запускает автоматический повтор мутации: сервер мог уже сохранить
изменение, поэтому перед повтором нужно обновить данные. Неизвестный SPA-путь показывает 404.
Результаты запусков доступны в [GitHub Actions](https://github.com/j2m5/gotest/actions).

`audit` — отдельная сетевая проверка: она завершает CI с ошибкой при advisory уровня
moderate/high/critical, включая devDependencies, а также при сбое получения отчёта.
`check` сохраняет локальные проверки без обязательного запроса к реестру. Обновления
зависимостей проверяйте через чистый `npm run setup`, затем `npm run audit` и `npm run check`;
изменения frontend/package.json и frontend/package-lock.json сохраняйте вместе. Нулевой отчёт означает
отсутствие известных npm advisory для текущего дерева зависимостей на момент проверки.
`audit:go` отдельно проверяет достижимость известных Go-уязвимостей, включая тесты. Минимальная
исправленная версия Go закреплена в go.mod; при включённом стандартном GOTOOLCHAIN=auto
Go загрузит нужный toolchain. Обновление зависимостей также проверяйте через audit:go и test:race.

Порядок обслуживания, расписания, состояние очереди и восстановление БД с почтовым ключом
описаны в [`docs/operations.md`](docs/operations.md).

## Логи и проверки доступности

API пишет JSON-логи через стандартный `log/slog` в stderr. Каждому запросу назначается
новый случайный `X-Request-ID`: он возвращается в заголовке ответа и связывает записи
обработчика с итоговым событием `http_request`. Входящий X-Request-ID не переиспользуется.
При разборе ошибки сохраните этот заголовок из вкладки Network браузера и найдите
соответствующий `request_id` в серверном логе.

`http_request` содержит method, path (без query string), status, bytes (тело ответа),
duration_ms и aborted. Для 5xx и оборванных ответов используется ERROR; остальные запросы
пишутся на INFO. Ошибки фоновой доставки записываются отдельно на WARN с job_id, kind
и номером попытки. Данные форм, Cookie, Authorization, query-параметры и сырые
сообщения SQL/SMTP в эти записи не включаются. Для ошибок сохраняются error_kind,
error_type и, если применимо, SQLSTATE; ошибки конфигурации содержат имя настройки и
ограничение без её значения. Путь запроса виден в логах: секреты должны передаваться
в теле или query, а не в сегментах пути.

Паника до начала ответа даёт обычный JSON 500/internal_error; стек сохраняется только
на сервере, значение паники не записывается. Если заголовки или часть тела уже отправлены,
соединение обрывается и журнал получает aborted=true вместе с фактически начатым статусом.
Ошибки запуска отмечаются событием application_failed и полем stage; http_started
появляется только после успешного открытия порта. Остановка отмечается http_stopping/http_stopped.

Проверки доступны на порту Go API без сессии и собранного frontend:

| Маршрут | Назначение |
| --- | --- |
| GET /healthz | Живость HTTP-сервера; 200 с `{"status":"ok"}`, без обращения к БД |
| GET /readyz | Ping PostgreSQL с таймаутом до 2 секунд; 200 при успехе, 503/not_ready при ошибке, остановке или отсутствии проверки |

Оба маршрута поддерживают HEAD, возвращают X-Request-ID и Cache-Control: no-store.
Например: `curl.exe -i http://localhost:8081/readyz` на Windows или
`curl -i http://localhost:8081/readyz` на Linux. Проверяйте именно порт API;
Vite проксирует только /api. Readiness проверяет соединение с БД, а миграции и сиды
по-прежнему применяются отдельными командами перед запуском.

## Очистка истёкших сессий, токенов и почтовой очереди

После применения всех миграций, включая `20261027000200_mail_jobs`, можно запустить:

~~~powershell
npm run cleanup -- -dry-run
npm run cleanup -- -batch-size 1000 -timeout 1m
~~~

Команда загружает `.env` и использует только DATABASE_URL; переменная окружения имеет
приоритет. HTTP и почтовые настройки ей не нужны. Доступен прямой запуск
`go run ./cmd/cleanup`; после `npm run build` — `.local/bin/cleanup.exe` на Windows
или `.local/bin/cleanup` на Linux. Рабочая папка определяет расположение `.env`.

В начале прохода фиксируется время PostgreSQL. Удаляются sessions с expires_at и
email_verifications с expired_at и password_resets с expires_at не позднее этой отметки.
Из mail_jobs удаляются просроченные задания и задания с окончательной ошибкой старше
24 часов; задания с действующей арендой worker остаются до следующего прохода. Каждый DELETE обрабатывает
до batch-size строк, начиная с самых старых. По умолчанию batch-size=1000, допустимо
1..10000; таблицы обрабатываются поочерёдно короткими транзакциями. Аккаунты, персонажи
и users.character_id не изменяются. Истечение сессии проверяется при авторизации
независимо от запуска очистки.

`FOR UPDATE SKIP LOCKED` пропускает записи, занятые другим запросом: они будут доступны
следующему проходу после освобождения. Записи, истёкшие уже после времени отсечения,
также остаются до следующего запуска. Поэтому успешный проход не гарантирует, что
в момент его завершения вообще нет просроченных строк. Параллельные запуски допустимы.

`-dry-run` только считает подходящие строки, включая занятые: удалений и блокировок строк
нет. Это оценка на момент проверки; она может отличаться от результата следующего запуска.
Для отбора используются индексы `(expires_at,id)` и `(expired_at,id)`.
Откат миграции индексов sessions/email_verifications сохраняет данные; индекс
password_resets удаляется вместе с таблицей при откате миграции восстановления пароля.

По умолчанию весь запуск, включая подключение, ограничен минутой; само подключение —
не более 10 секунд. Ctrl+C/SIGTERM или ошибка завершают команду с ненулевым кодом.
Ранее подтверждённые пакеты уже зафиксированы. При потере соединения в момент commit
исход последнего запроса может быть неизвестен, поэтому счётчики ошибки показывают
подтверждённые удаления, а не гарантированное итоговое число. Повторный запуск безопасен.

Бинарник пишет JSON в stderr: cleanup_preview содержит sessions_matched/verifications_matched/password_resets_matched/mail_jobs_matched,
cleanup_completed — sessions_deleted/verifications_deleted/password_resets_deleted/mail_jobs_deleted; также выводятся cutoff,
число непустых пакетов batches и duration_ms. cleanup_failed содержит этап и безопасную
категорию ошибки, а при сбое очистки — накопленные подтверждённые счётчики. Токены и
строка подключения в лог не включаются. Справка: `npm run cleanup -- -help`.

Очистка запускается отдельно от API. Автоматического расписания пока нет; для него
можно использовать собранный бинарник с тем же окружением и выбранной рабочей папкой.

### Срок хранения боевых журналов

После миграции `20261113000100_battle_log_retention` подробный журнал завершённого
боя можно очистить через **30 дней** от `ended_at`. Для этого явно включите флаг:

~~~powershell
npm run cleanup -- -battle-logs -dry-run
npm run cleanup -- -battle-logs -timeout 1m
~~~

Флаг добавляет боевые журналы к обычной очистке сессий/токенов/почты. Без него
поведение команды прежнее. Возраст считается по времени PostgreSQL: 30 × 24 часа,
одна отметка отсечения на весь проход. Активные и недавно завершённые бои остаются.

Сохраняются сам бой, снимок правил, квитанции применённых умений и последнее событие
с исходом и фактической наградой. Кошельки, опыт, ресурсы, CD и NPC не меняются.
Повтор старой команды возвращает прежнюю квитанцию; новая команда завершённому бою
отклоняется. Небольшие результаты и квитанции пока хранятся бессрочно.

Каждый боевой пакет обрабатывает **один бой** за транзакцию, независимо от
`batch-size` строк для остальных таблиц. Пакеты чередуются с остальными видами
очистки. Занятые бои пропускаются через `FOR UPDATE SKIP LOCKED`; параллельные
запуски допустимы. Метаданные `battle_log_archives` и удаление подробностей
фиксируются вместе. Ошибка или отмена откатывает текущий пакет; ранее подтверждённые
пакеты сохраняются. Некорректный конечный снимок/событие останавливает проход с ошибкой,
сохраняя этот журнал. `dry-run` только считает кандидатов и не блокирует строки.

Логи команды дополнительно содержат `battle_log_cutoff`; для предварительного
подсчёта — `battle_logs_matched`/`battle_events_matched`, для выполненной очистки —
`battle_logs_cleared`/`battle_events_deleted`. Последнее событие в число удалений
не входит. Потеря ответа на commit допускает неопределённость последнего пакета,
как и в остальных видах очистки; повторный запуск безопасен.

В `/api/battles/detail` поле `log_cleared_at` равно `null` для полного журнала.
После очистки оно содержит время очистки, `events` — только итоговое событие,
`next_after=null`, а `after_sequence` игнорируется. Клиент заменяет накопленную
историю этим итогом и показывает сообщение об истёкшем сроке хранения; награда
остаётся видна. Метаданные и события читаются в одном согласованном снимке БД.

Миграция сохраняет существующие данные. Её откат допустим до первой очистки;
после появления архивных отметок down явно отказывает. Удалённые подробности
можно вернуть только из резервной копии, поэтому предварительный подсчёт доступен
отдельно. Автоматического запуска очистки боёв пока нет.

## Справочники и сиды

После применения **всех миграций**, включая `20261025000200_seed_codes`, выполните:

~~~powershell
go run ./cmd/seed
~~~

Команда загружает `.env`, но использует только `DATABASE_URL`: настройки HTTP и почты
для неё не нужны. Все SQL-файлы из `seeds/` выполняются по имени в одной транзакции.
Об успешном применении файлов сообщается после commit. Ошибка, прерывание или таймаут
откатывают изменения всего запуска; пустая/отсутствующая папка и пустой SQL-файл — ошибка.

Можно задать другой путь (относительно рабочей папки или абсолютный) и общий таймаут:

~~~powershell
go run ./cmd/seed -dir ./seeds -timeout 30s
~~~

По умолчанию общий таймаут — одна минута, подключение к БД ограничено десятью секундами.
SQL-файлы сидов не должны содержать собственные BEGIN/COMMIT/ROLLBACK.

Фракции, классы и способности имеют постоянный уникальный `code`, независимый от названия
и числового ID. Связи в сидах разрешаются по кодам. Повторный запуск добавляет недостающие
записи и связи, сохраняя существующие ID, названия, характеристики и пороги опыта.
Для изменения уже настроенного баланса нужна отдельная миграция: seed его не перезаписывает.
Как и при обычном PostgreSQL INSERT, пропущенные вставки и откаты могут оставлять пробелы
в SERIAL-последовательностях; непрерывность ID не требуется.

Миграция кодов сохраняет существующие записи и ссылки на них. Старые стандартные фракции
и классы распознаются по названиям и принадлежности к фракции; способности — по сочетанию
названия и иконки, поскольку названия повторяются. Неизвестные/переименованные записи
получают коды `legacy_faction_<id>`, `legacy_class_<id>`, `legacy_ability_<id>`.
При необходимости их можно вручную сопоставить со стандартными кодами **до запуска seed**,
иначе seed добавит недостающие стандартные записи отдельно.

Если старые повторные запуски уже создали несколько записей с одним стандартным кодом,
миграция прерывается целиком с сообщением `duplicate legacy ...`. Дубликаты нужно разобрать
с учётом ссылок персонажей и справочников; автоматического удаления или объединения нет.
Down-миграция удаляет только столбцы кодов и их ограничения, сохраняя данные и числовые ID.
После неё новые сиды требуют повторного применения up-миграции.

## Каталог планет

Миграция `20261104000100_planets` и `seeds/07_planets.sql` добавляют 100 миров:
15 миров неотчуждаемого ядра каждой фракции и 70 обычных. Начальный контроль:
25 миров у Республики, 25 у Империи, 50 нейтральных. Из 25 владений каждой стороны
10 обычных миров допускают смену контроля; ядро остаётся неизменным.

`core_faction_id` задаёт принадлежность к ядру, `controlling_faction_id` — текущий

Ограничение и триггер запрещают смену принадлежности к ядру и потерю его владельца.

Модуль `internal/world` предоставляет каталог через `GET /api/world/planets` для

Прибытие выбирается по минимальному `recommended_level`, затем `position` и `id`.

для создания персонажей. Down-миграция удаляет позиции/локации, сохраняя персонажей
и справочник планет; повторный up назначает столицы заново.

`GET /api/world/navigation?character_id=…` возвращает текущую позицию и доступность
миров. `POST /api/world/travel` принимает `character_id`, `planet_id` и `from_location_id`;
проверяет выбранного персонажа, сессию, бан, исходную позицию и актуальный контроль
в одной транзакции. Перелёт мгновенный и бесплатный. Повторное действие на текущую
планету сохраняет локацию. Потеря доступа отображается при чтении; следующее
актуальное действие перемещения возвращает персонажа в столицу.

принадлежать текущей планете. Старая ссылка после перелёта возвращает `planet_changed`;
кнопка «Назад» и перезагрузка не меняют позицию. После успешного перемещения общий
список персонажей получает новое чтение, даже если прежний фоновый запрос ещё не завершён.

Первичное наполнение мира завершено; перемещения и PvE-бои в доступных локациях
реализованы. Вторжения, главные приказы и основания доступа через галактическую
войну остаются отдельными этапами.

Начальные внешние владения выбраны по соседним областям сетки
[The Essential Atlas](https://lumiere-a.akamaihd.net/v1/documents/starwars_7c65cf9e.pdf).
Контроль — игровая конфигурация, а не точное воспроизведение исторических границ.
Координаты для будущей карты этим этапом не задаются.

## Противники на локациях

размещение с уровнем и рангом (`location_npcs`) и общие экземпляры (`npc_spawns`).
У экземпляра постоянный ID и номер слота внутри размещения. Все игроки в одной
локации видят один набор экземпляров; чтение списка не создаёт новых NPC.

и NPC всех двадцати начальных внешних владений. `seeds/13_core_worlds.sql`,
`seeds/14_core_worlds.sql` и `seeds/15_core_worlds.sql` заполняют ещё по шесть миров ядра.
`seeds/16_core_worlds.sql` завершает ядро, добавляя последние восемь миров.
`seeds/17_neutral_worlds.sql` добавляет контент первых восьми нейтральных миров.
`seeds/18_neutral_worlds.sql` добавляет ещё восемь нейтральных миров.
`seeds/19_neutral_worlds.sql` расширяет нейтральную часть ещё на восемь миров.
`seeds/20_neutral_worlds.sql` добавляет восемь миров в области влияния хаттов.
`seeds/21_neutral_worlds.sql` добавляет девять нейтральных миров.
`seeds/22_neutral_worlds.sql` завершает первичное наполнение всех 100 миров.
Всего 415 шаблонов, 3000 размещений и 4000 экземпляров на 1000 локациях 100 планет.
На локацию приходится два обычных противника,
один сильный и один элитный. Начальные уровни: рекомендация локации, +2 и +4
соответственно, не выше максимума справочника уровней (сейчас 50). Уровень и ранг
хранятся в размещении и могут настраиваться независимо от шаблона. Повторный seed
сохраняет ID, тексты и ручные изменения баланса.

## Кошельки и валюта

Миграция `20261104000400_wallets` создаёт кошелёк кредитов (`credits`) для каждого
персонажа и кошелёк монет картеля (`cartel_coins`) для аккаунта. Монеты картеля
общие для всех его персонажей. Начальные балансы равны нулю; новые кошельки
создаются триггерами вместе с владельцем, существующие — при миграции.
Seed не начисляет валюту и не сбрасывает балансы.

`wallets` хранит целочисленный BIGINT-баланс, `wallet_entries` — неизменяемые
операции с суммой, причиной и остатком до/после. Баланс не может стать отрицательным,
арифметика проверяет переполнение. У каждой операции серверные `source` и
`operation_key`: повтор возвращает исходный результат, а изменение суммы или
описания с тем же ключом вызывает конфликт. Ключ уникален внутри кошелька;
для награды, выдаваемой каждому персонажу отдельно, источник должен включать
ID персонажа в ключ события, если используется общий кошелёк монет картеля.

Начисления и траты доступны только доверенному серверному коду через `wallet.Service`.
`WalletRepository.Apply` выполняет свою транзакцию. Для общей награды есть
`WalletRepository.ApplyInTx` и `ProgressionRepository.GrantInTx`: PvE использует их
для сохранения исхода, опыта, кредитов и журнала в одной транзакции с ключом
`pve:<battle-id>`. Сами методы не коммитят транзакцию; вызывающий код обязан
сделать rollback при любой ошибке.
Порядок блокировок: персонаж, затем кошелёк. Не объединяйте отдельные вызовы
`Grant` и `Apply`, если результат должен быть атомарным.

Чтение требует действующую сессию и выбранного персонажа:

- `GET /api/wallet?character_id=…` — кредиты персонажа и монеты картеля аккаунта.
- `GET /api/wallet/history?character_id=…&before=…` — до 20 операций по убыванию ID;
  `next_cursor` передаётся в следующий запрос, NULL означает конец истории.

Суммы и ID записей передаются в JSON десятичными строками, чтобы сохранить весь
диапазон BIGINT без округления в JavaScript. Frontend форматирует их через BigInt.
Внутренние ключи событий и владельцы кошельков не входят в публичный ответ.
HTTP-методов выдачи/списания, платежей и магазинов сейчас нет.

Баланс в футере игровых страниц ведёт на `/wallet` с историей операций.
Переход между персонажами меняет кредиты, сохраняя общие монеты картеля.
Есть обновление, повтор после ошибки и загрузка следующей страницы; старые ответы
после смены аккаунта/персонажа игнорируются. Кошельки других игроков не раскрываются
через публичный профиль.

Удаление владельца удаляет его кошелёк и историю. Down-миграция отказывается
удалять ненулевой баланс или непустой журнал: потеря записей позволила бы повторно
начислить уже полученные награды. Перед обновлением БД используйте резервную копию.

## Аккаунт и персонажи

User — аккаунт с несколькими персонажами. Nullable-поле `users.character_id` содержит
активного персонажа, общего для всех сессий и устройств аккаунта. NULL означает отсутствие
выбора. При выходе из действующей сессии выбор сбрасывается для всего аккаунта, а удаляется
только текущая сессия; остальные устройства остаются авторизованными.

Миграция `20261025000300_character_integrity` закрепляет правила на уровне PostgreSQL:

- `(users.id, users.character_id)` ссылается на `(characters.user_id, characters.id)`:
  активным может быть только свой существующий персонаж.
- `(characters.class_id, characters.faction_id)` ссылается на соответствующую пару в classes:
  класс и фракция персонажа должны совпадать.
- `users.character_id` имеет тип INTEGER, как `characters.id`; в Go ему соответствует `*int`.
- Справочники содержат четыре базовых класса Империи и четыре Республики, без подклассов.

Чтобы удалить активного персонажа, сначала нужно сбросить выбор. Удаление всего аккаунта
каскадно удаляет его персонажей. При старых несовместимых связях миграция останавливается
целиком с диагностикой, не удаляя данные. Down-миграция снимает новые ограничения,
возвращает прежний тип BIGINT и сохраняет строки.

Миграции, меняющие типы столбцов, применяйте при остановленном приложении; после них запустите
приложение заново, чтобы соединения pgx не использовали старые подготовленные планы запросов.

Сброс активного персонажа и отзыв сессии при logout выполняются одной транзакцией.
Повторный logout с уже отозванным токеном не изменяет более поздний выбор. Истёкший токен
удаляется, но больше не даёт права менять выбор аккаунта.

Nullable avatar/description/icon в контрактах `character` представлены `*string`:
NULL и пустая строка сохраняют разные значения при чтении каталога, списка и выборе персонажа.
Для SQL-полей без прикладного потребителя (например, characters.activated_at)
отдельные Go-модели не создаются; их nullable-семантика проверяется SQL-тестами.
`users.role_id` (SMALLINT) соответствует `int16` в `auth.Identity`.
Каталог возвращает в `name` непустой `alias` без пробелов по краям, иначе исходное
название. Так интерфейс использует русские подписи из БД; для идентификации служат `code` и `id`.

После входа открывается `/characters` со списком персонажей, либо `/game`, если персонаж
уже выбран. `/characters/new` создаёт персонажа с именем, фракцией и классом из справочника.
При смене фракции выбор класса сбрасывается; список содержит только совместимые классы.
Создание возвращает к списку. Вход за персонажа выполняется отдельно кнопкой «Играть».
На экране персонажа кнопка «К выбору персонажа» явно сбрасывает общий выбор аккаунта.
Обычные переходы и GET-запросы выбор не меняют.

Имя содержит 3–32 символа: латинские/кириллические буквы, пробел, дефис, ASCII-апостроф;
начинается и заканчивается буквой. Убираются пробелы по краям, повторные обычные пробелы
сжимаются, Unicode приводится к NFC. Имена уникальны без учёта регистра во всей игре.
Миграция `20261025000400_character_names` закрепляет нормализованный уникальный ключ в БД.
Для кириллицы и латиницы используется отдельная ICU collation `character_name_unicode`,
поэтому правило не зависит от системной локали базы. При конфликтующих старых именах
миграция прерывается целиком, не переименовывая и не удаляя персонажей. Down сохраняет
данные и возвращает прежнее ограничение уникальности с учётом регистра.
Минимальная версия PostgreSQL повышена с 12 до 14 из-за SQL-функции с разобранным телом
`RETURN` и поддержкой Unicode-нормализации; [описание SQL-функций](https://www.postgresql.org/docs/14/sql-createfunction.html)
и [ICU collation](https://www.postgresql.org/docs/14/collation.html).

Новый персонаж получает SQL-значения по умолчанию (уровень 1, роль `dd`, начальные
характеристики) и способности своего класса в одной транзакции. Создание и выбор сначала
блокируют аккаунт, затем заново проверяют сессию: запрос, ожидавший завершения logout,
не может восстановить выбор с отозванной сессией.

Frontend хранит состояние аккаунта централизованно. Выбор с другого устройства обновляется
при возвращении во вкладку и каждые 15 секунд в видимой вкладке. Перекрывающиеся обновления
объединяются; запоздавшие ответы не отменяют новый вход, выход или локальный выбор.
`/game` показывает оформление фракции и ссылку «Галактическая война» на `/galaxy`.
Общая оболочка игровых страниц содержит полосы здоровья/энергии, имя и уровень
персонажа, баланс валют и навигацию; при активном бое доступна ссылка возврата в него.
`/profile` — собственный профиль активного персонажа с портретом, классом, фракцией,
уровнем, текущим опытом и HP/MP. Без активного персонажа маршрут возвращает к выбору,
без сессии — ко входу. Переход в профиль не меняет выбор и не завершает активный бой.

`/characters/:characterId` — публичный профиль персонажа для авторизованных игроков,
включая игроков без выбранного персонажа. Ник в чате/форуме ведёт к персонажу — автору
публикации, даже после смены его владельцем активного персонажа. В списке модераторов
ссылка ведёт к указанному выбранному персонажу; если его нет, ник остаётся обычным текстом.
Публичный профиль содержит имя, аватар, класс, фракцию, уровень и текущую роль аккаунта.
Почта, другие персонажи аккаунта, опыт и ресурсы в этот ответ API не входят.

Оболочка сохраняет прежние цвета и ширину до 480 px. Используемая графика лежит в
`frontend/public/images`, отдельный PHP-архив для запуска не нужен. До выбора собственного
аватара показывается стандартный портрет класса, если он есть, иначе эмблема фракции.
Поле avatar принимает только локальные пути изображений; при отсутствующем файле
интерфейс показывает запасную эмблему. Внешние URL изображений не загружаются.

### Ограничения игровых данных

Миграция `20261025000700_character_stats_integrity` закрепляет правила в PostgreSQL:

| Поле | Правило |
| --- | --- |
| class_id + role | Связка должна существовать в class_roles |
| level | Уровень должен существовать в levels |
| experience | Неотрицательное число |
| hp, hp_current | hp > 0; текущее здоровье от 0 до hp включительно |
| mp, mp_current | mp >= 0; текущий ресурс от 0 до mp включительно |
| mastery, endurance, power, accuracy, alacrity, critical, defense, shield, absorption | Неотрицательные значения |
| levels.level, levels.experience_required | Положительный номер уровня и неотрицательный порог опыта |

Нулевое текущее HP допустимо; персонаж без MP хранит mp=mp_current=0. При уменьшении
максимума ниже текущего значения оба поля нужно изменять одним UPDATE. Характеристики
хранят числовые значения без искусственного потолка 100; верхняя граница задаётся типом
INTEGER. Максимальный уровень определяется справочником: расширение за текущие 50
уровней не требует изменения ограничения. Начислением опыта и повышением уровня
управляет серверный сервис progression, описанный ниже.

Роль проверяется также при смене класса. Удалить или изменить используемую запись
class_roles/levels нельзя, пока на неё ссылаются персонажи. Индексы
characters_class_role_idx и characters_level_idx поддерживают эти внешние ключи.
Справочники должны быть заполнены перед созданием персонажей: SQL defaults остаются
`role='dd'`, `level=1`, `experience=0`, HP/MP=100. Отсутствие нужной строки справочника
прерывает создание целиком и считается внутренней ошибкой конфигурации данных.

Up-миграция блокирует characters, class_roles и levels, проверяет старые строки и
добавляет все ограничения одной транзакцией. При нарушении выдаётся категория ошибки
`character stats:`; исправьте справочник или данные осознанно и повторите миграцию.
Автоматического исправления значений нет. Down удаляет добавленные ограничения и
два индекса, сохраняя данные, defaults и прежние правила владения/класса/фракции.

### Восстановление ресурсов и умения

HP восстанавливается от нуля до максимума за пять минут, энергия — за минуту,
включая время боя. Сервер рассчитывает ресурс по сохранённому значению и времени
его изменения; отдельная запись в БД на каждый тик не нужна. Полный ресурс не копит
дополнительное восстановление. Браузер получает серверное время и метаданные для
плавного отображения; право на расход проверяет сервер.

Миграция `20261108000100_resource_precision` добавляет дробные остатки
`hp_regen_remainder` и `mp_regen_remainder`. Остаток — целый числитель, знаменатель
равен периоду восстановления в миллисекундах (300000 / 60000). Частые попадания
и затраты энергии сохраняют накопленную долю единицы ресурса. Старые значения,
временные якоря и персонажи при миграции сохраняются.

Для игровых изменений используется `db.ChangeCharacterResourcesInTx`: блокировка
персонажа, расчёт восстановления и запись изменения входят в транзакцию вызывающего
кода. MP нельзя потратить сверх доступного; HP после смертельного урона ограничивается
нулём. Ошибка расхода не меняет ни один ресурс. `resources_revision` отличает полный
снимок helper от прямой SQL-замены: обычный UPDATE ресурса сбрасывает его временной
якорь и остаток. Игровые действия должны использовать helper, чтобы сохранить доли.

Миграция `20261108000200_ability_cooldowns` добавляет `abilities.cooldown_ms`,
`character_abilities.ready_at` и `characters.global_cooldown_ready_at`. Личный CD
задаётся отдельно для каждого шаблона, начальное значение — 1500 ms; общий GCD —
1500 ms. Готовность сохраняется между сессиями, боями и сменами персонажа.
`damage` / `heal` — базовые величины эффекта; формулы характеристик и защиты находятся
в боевом модуле. Миграция заменяет только стандартные описания с PHP-заглушкой `%d%`,
сохраняя пользовательские тексты и баланс; down не возвращает устаревшие описания.

`GET /api/abilities?character_id=…` возвращает изученные умения выбранного персонажа,
доступные его классу, снимок ресурсов, серверное время и причины недоступности:
`ready`, `cooldown`, `global_cooldown`, `insufficient_energy`, `defeated`. Чтение
не запускает CD и не расходует энергию. Клиент `characterAbilities` передаёт
`X-Account-ID` и регистрирует время получения ресурсов для браузерной проекции.

`AbilityRepository.PrepareUseInTx` — внутренний шаг игровой транзакции:
проверяет изученность, класс, HP, MP и CD/GCD, списывает энергию и записывает таймеры.
Блокировки берутся в порядке персонаж → изученное умение, время — после блокировок.
Вызывающий боевой модуль обязан проверить аккаунт, бой и цель, устранить повтор
команды, затем применить эффект и записать событие в **той же транзакции**. При любой
ошибке её нужно откатить целиком. PvE использует тот же расчёт внутри своей транзакции;
`ready` означает готовность умения по ресурсам и времени, а не разрешение атаковать цель.

### Жизненный цикл PvE

Миграция `20261108000300_battle_lifecycle` добавляет `battles` и
`npc_spawns.respawn_at`. Два частичных UNIQUE-индекса разрешают только один активный
бой на персонажа и на экземпляр NPC. Занятость определяется записью боя, без
дублирующих флагов. `GET /api/npcs` скрывает занятых и ожидающих возрождения NPC.
Идентификатор боя — BIGINT; API передаёт его десятичной строкой для точности JavaScript.

`CombatRepository.StartInTx` — внутренний шаг серверного исполнителя, работающий
в транзакции READ COMMITTED. Он проверяет сессию, бан, выбранного персонажа, позицию,
доступ к планете, положительное HP, размещение/доступность NPC. Порядок блокировок:
аккаунт → персонаж → каталог места/NPC → экземпляр → бой. Проверки занятости и
серверного времени выполняются после получения блокировок; перед записью сессия
проверяется повторно. `NPCStats` передаётся отдельно от параметров действия и должен
вычисляться доверенным серверным кодом, а не приниматься от клиента. Публичный
`CombatRepository.Start` сам вычисляет баланс и создаёт сроки исполнения и событие
начала в той же транзакции; новые PvE-встречи создаются только этим методом.

`start_key` уникален внутри персонажа. Повтор для того же NPC/исходной локации
возвращает тот же бой с его текущим состоянием, даже если он завершён. Использование
ключа для другой цели/локации возвращает конфликт. Начальные параметры встречи
неизменны; новый бой получает свежий полный ресурс NPC.

`RetreatInTx` завершает встречу, полностью восстанавливает NPC и освобождает его,
сохраняя реальные HP/MP и CD/GCD игрока. Потеря доступа к планете не мешает отступить.
Доверенный `DefeatInTx` предназначен для завершения в текущий момент и оставляет
персонажа на месте с 0 HP; XP, деньги, MP и кулдауны не сбрасываются. PvE-исполнитель
завершает бой своим общим путём, сохраняющим события и точное время смертельного
удара: после простоя сервера регенерация отсчитывается от удара. Повтор завершения
не меняет состояние и не затрагивает новую встречу этого NPC. Все операции возвращают
`Replayed`, чтобы вызывающий код не повторял события, и требуют rollback при ошибке.

Перелёт и локальное перемещение во время активного боя возвращают
`409 character_in_battle`, включая возврат с потерянной планеты. Logout и смена
персонажа не завершают бой. `GET /api/battles/current?character_id=…` возвращает
согласованный снимок персонажа и его активного боя либо `battle: null`.
Клиент `currentBattle` передаёт контекст аккаунта и учитывает время получения ресурсов.
Down-миграция отклоняется при наличии любых боёв, сохраняя состояние и историю.

### Исполнение PvE

Миграция `20261108000400_combat_execution` добавляет `battle_executions` со снимком
правил и сроками, `battle_events` с последовательным журналом и `battle_commands`
с ключами уже применённых действий. У боя добавлены исходы `won` и `expired`.
Примените миграцию до запуска нового API. Down отказывается удалять непустые
таблицы исполнения или историю побед/истечения; пустой up/down сохраняет мир
и персонажей.

Два worker в горутинах выбирают наступившие действия через
`FOR UPDATE OF characters SKIP LOCKED`. Они работают независимо от вкладок,
logout и выбранного персонажа, используют PostgreSQL-время после блокировок
и завершаются вместе с сервером. Временные отметки и шаг паттерна переживают
рестарт; пропущенные удары рассчитываются по порядку с регенерацией между ними.
Пустая очередь проверяется через 250 ms; операция ограничена пятью секундами.
Отдельной горутины на каждый бой нет.

Миграция `20261110000100_combat_retries` добавляет `retry_count` и `retry_at`.
Ошибка отдельного боя откатывает его действие до savepoint, затем сохраняется
срок повтора: через 1, 2, 4, 8, 16 и далее каждые 30 секунд. Счётчик ограничен 6.
Остальные встречи продолжают обрабатываться без общей паузы. Срок повтора хранится
в PostgreSQL, поэтому действует для всех процессов и сохраняется после рестарта.
Исходные `next_action_at`/`expires_at` не сдвигаются: после устранения причины бой
догоняет своё расписание. Успешное действие исполнителя или игрока сбрасывает
задержку; команды игрока не ждут `retry_at`. Повреждённые данные автоматически
не исправляются, причина ошибки требует устранения. В логе есть `battle_id`,
`character_id`, `retry_at` и безопасная категория ошибки, без исходного текста SQL.
Если сбой соединения/отмена операции не позволяет сохранить повтор, транзакция
откатывается целиком и исполнитель ждёт 1 s перед новой попыткой. Down удаляет
только служебные поля повторов и возвращает прежний индекс очереди.

`tests/db/combat_due_test.go` проверяет пропуск ошибочного боя, откат при настоящей
ошибке SQL, сохранение/ограничение задержки, конкуренцию исполнителей и восстановление
через команды игрока. Отдельные тесты проверяют up/down миграции и безопасный лог.

Команды доступны через защищённый API:

| Метод / путь | Параметры |
| --- | --- |
| POST `/api/battles/start` | `character_id`, `location_id`, `npc_spawn_id`, `request_key` |
| POST `/api/battles/use` | строковый `battle_id`, `character_id`, `ability_id`, `request_key` |
| POST `/api/battles/retreat` | строковый `battle_id`, `character_id` |
| GET `/api/battles/detail` | `battle_id`, `character_id`, необязательный `after_sequence` |

POST принимает JSON, GET — query; клиент приложения передаёт `X-Account-ID`.
Ключ действия сохраняется для повторной отправки того же запроса. Тот же ключ
с другим умением/целью возвращает конфликт. Сервер сначала обрабатывает наступившие
атаки NPC, затем действие игрока; при равном времени истечение срока предшествует
атаке. Смертельный удар нельзя отменить отступлением. Отказ применения из-за
MP/CD не откатывает уже наступившие атаки. Ошибка SQL откатывает всю транзакцию.
Начало, эффект умения, расход MP, CD/GCD, события и награды не допускают частичной записи.

Победа один раз выдаёт опыт персонажу и кредиты в его кошелёк через существующие
progression/wallet, с ключом `pve:<battle-id>`. На максимальном уровне XP не растёт,
кредиты выдаются; монеты картеля не затрагиваются. NPC возрождается через 30 секунд.
Отступление, поражение или истечение встречи полностью восстанавливают и освобождают
NPC без награды; ресурсы игрока продолжают восстанавливаться обычным способом.

Начальный баланс вынесен в `internal/combat/balance.go` и пока экспериментальный.
HP NPC = `(48 + 12 × level) × rankMultiplier`, множители normal/strong/elite = 1/2/3.
Обычный удар через 2 s, сильный через 3 s; паттерн зависит от ранга. Опыт =
`5 × level × rankMultiplier`, кредиты = `3 × level × rankMultiplier`.
Встреча длится максимум десять минут; минимальный интервал правил — секунда,
поэтому восстановление после простоя обрабатывает не более 600 пропущенных атак.
Правила фиксируются при начале встречи, изменения баланса относятся к новым боям.

Журнал хранит реальные действия и фактические HP/MP/урон/лечение/награды,
без событий на каждую секунду регенерации. Чтение по `after_sequence` возвращает
до 50 событий и `next_after` для следующей страницы; завершённые встречи доступны
владельцу выбранного персонажа. Клиентские функции combat типизированы и
регистрируют время получения ресурсов. `event_sequence` в ответе команды относится
к исходному действию, в том числе при повторе; курсор журнала строится только по
полученным событиям.

Подробности завершённых боёв можно очистить через 30 дней, сохранив итог,
награду и квитанции команд. Срок считается от окончания боя; очистка запускается
отдельной командой. Правила и команды описаны в разделе
[«Срок хранения боевых журналов»](#срок-хранения-боевых-журналов).

### Экран боя

Кнопка «Атаковать» в списке NPC открывает `/battle/:battleId`. Экран показывает HP
противника, умения с личными CD и GCD, расход энергии, журнал, исход и фактическую
награду. Можно отступить или вернуться к локациям после завершения. На остальных
игровых страницах активная встреча доступна через «Вернуться в бой». Перезагрузка,
смена персонажа и logout не завершают встречу: NPC продолжает действовать на сервере.

`features/abilities/ui/AbilityBar` получает готовые действия и `onUse`, не зависит
от PvE, HTTP и противника. Чистая `projectActions` проецирует ресурсы/CD от времени
сервера и монотонного времени браузера; системные часы игрока не влияют на отсчёт.
Недоступное умение остаётся в панели с причиной и сохраняет фокус клавиатуры.

`CombatSession` управляет чтением, пагинацией журнала и командами. Старые чтения
отменяются перед действием, поздние ответы другого аккаунта/персонажа игнорируются.
Повторный клик не создаёт вторую команду. При неопределённом сетевом исходе доступен
явный повтор с прежним ключом; автоматической повторной отправки действий нет.

`GET /api/battles/events?account_id=…&character_id=…` — WebSocket с cookie и проверкой
Origin, сессии, бана и выбранного персонажа. Он передаёт только `{"type":"changed"}`
для своего персонажа. Репозиторий уведомляет после commit, включая наступившие
атаки NPC при отклонённом умении; rollback и чистый повтор сигнал не создают.
Игровые данные клиент получает через защищённый HTTP API.

Hub действует в пределах процесса. Видимая вкладка дополнительно сверяется с API
раз в пять секунд, при reconnect и возвращении фокуса — это покрывает пропущенные
уведомления и другой процесс. Фоновые чтения не продлевают игровой онлайн. После
пробуждения замороженной вкладки клиент получает серверное состояние, включая исход.
Журнал следует за новыми событиями только пока игрок читает его конец.
После очистки подробностей он показывает сохранённый итог и сообщение об истечении
срока хранения. Накопленная в браузере история заменяется ответом сервера.

Проверки PvE входят в `npm run check`. `TestCombatBrowserFlow` проходит обычные
победу/отступление и мобильные размеры; `TestCombatReliabilityBrowserFlow` проверяет
два аккаунта на одном NPC, несколько вкладок, Enter/Space, потерю ответа после
commit, повтор команды, offline/reconnect, замороженную и обычную фоновую вкладку.
Go владеет процессом Chrome отдельно от Node-драйвера и завершает его при отмене
теста; это проверяется отдельным сценарием принудительной остановки драйвера.
`TestCombatRetentionBrowserFlow` проверяет очищенный журнал, сохранённый итог
и награду, перезагрузку страницы и мобильный экран.

`TestCombatSurvivesActualProcessCrash` запускает настоящий `cmd/app` в случайной
тестовой схеме, аварийно завершает его при ожидающей транзакции и во время боя,
затем сверяет журнал, сроки NPC, CD и повтор команды после нового запуска.
Серверные тесты также проверяют гонку удара/отступления/атаки NPC и единственную
награду. Эти сценарии используют `TEST_DATABASE_URL`. Нагрузка 100/500/1000
одновременных боёв проверяется отдельно командой `npm run test:combat-load`;
устройство стенда и границы измерения — в разделе
[«Нагрузочная проверка боёв»](#нагрузочная-проверка-боёв).

### Опыт и повышение уровня

`characters.experience` — общий накопленный опыт; `levels.experience_required` —
общий порог достижения указанного уровня. Например, при порогах 0 / 100 / 250
переход со второго на третий требует ещё 150 опыта. Опыт при повышении не обнуляется,
одна награда может повысить сразу несколько уровней.

`internal/progression` содержит чистый расчёт `Curve` и сервис `Service`;
`db.ProgressionRepository` сохраняет результат. Пороги и максимальный уровень
читаются из levels при каждом новом начислении. Числа баланса в Go не зашиты:
каталог должен начинаться с уровня 1 и порога 0, идти без пропусков, с возрастающими
порогами. Некорректный каталог отклоняет новое начисление без частичной записи.

При достижении максимального уровня сохраняется только опыт до его порога;
избыток отбрасывается. На максимуме последующие награды дают 0 XP. Изменение порогов
не отнимает уже заработанные опыт и уровень: новый порог влияет на последующие
начисления. Повышение порога существующего максимального уровня не включает набор
опыта снова; добавление нового уровня позволяет получать новые награды.
Массовый пересчёт существующих персонажей при балансировке требует отдельной операции.
Повышение уровня пока не меняет характеристики и не восстанавливает HP/MP.

Начисление доступно только серверному коду. PvE уже использует `GrantInTx` для
выдачи опыта в общей транзакции победы. Другие источники наград должны проверять
право персонажа на награду и определять сумму и ключ события на сервере.
Пример отдельного начисления для будущей системы заданий:

~~~go
xp := progression.NewService(db.NewProgressionRepository(pool))
result, err := xp.Grant(ctx, progression.Reward{
    CharacterID: characterID,
    Key:         "quest:123/attempt:7",
    Experience:  150,
})
~~~

Ключ уникален для персонажа: 1–128 ASCII-символов, первый — буква/цифра,
остальные — буквы, цифры или `:._/-`. Сумма — положительное int64. Повтор с тем же
ключом и суммой возвращает **исходный** результат с `Replayed=true`, без нового
начисления; другая сумма для использованного ключа — `ErrRewardConflict`.
`Change.Granted` показывает фактически выданный опыт, `Before`/`After` — состояние
при исходной операции. Для актуального состояния после других наград нужно перечитать
персонажа. Клиентского маршрута с произвольной суммой опыта нет; существующий API
персонажей уже возвращает уровень и общий опыт.

Миграция `20261025000800_experience_rewards` добавляет журнал
`character_experience_rewards`. Блокировка строки персонажа, обновление level/experience
и запись события выполняются одной транзакцией: параллельные награды не теряются,
повтор одного события не удваивает XP. Записываются даже нулевые начисления на максимуме,
чтобы после добавления уровней старые события не превратились в запас опыта.
Журнал хранится до удаления персонажа, без очистки по возрасту. Down допускается
только для пустого журнала; при наличии наград он останавливается, сохраняя защиту
от повторов. Для такого отката сначала нужен отдельный план сохранения истории.

### API персонажей

Все маршруты требуют действующей сессии. `user_id`, роль, уровень и характеристики
не принимаются от клиента. Входные JSON-объекты проверяются строго.

| Метод и маршрут | Вход | Успех |
| --- | --- | --- |
| GET /api/characters/catalog | Cookie | 200: factions, classes |
| GET /api/characters | Cookie | 200: characters, active_character_id |
| GET /api/characters/profile | Cookie, query character_id | 200: character (публичные поля) |
| POST /api/characters | name, faction_id, class_id | 201: character |
| PUT /api/characters/active | character_id: число или null | 200: character или null |

Пустой объект при выборе — ошибка: для сброса требуется явное `{"character_id":null}`.
При выборе 404 одинаков для чужого и несуществующего персонажа. Публичный профиль
разрешает просмотр чужого персонажа, а для несуществующего возвращает 404;
отсутствующий или некорректный character_id — 400. При создании 409 — занятое имя;
422 — недопустимое имя, ID или сочетание класса и фракции. Остальные HTTP-правила
совпадают с авторизацией: 401, JSON-ошибки, лимит тела, запрет чужого origin и no-store.

## Почтовые драйверы

### local

~~~dotenv
MAIL_DRIVER=local
MAIL_FROM=noreply@example.test
MAIL_DIR=.local/mail
~~~

Каждое письмо сохраняется парой файлов с одинаковым именем: `.eml` с MIME-заголовками
для почтового клиента и `.txt` с читаемым текстом для редактора. В `.txt` ссылка целиком
записана на одной строке и пригодна для копирования в браузер без декодирования.
Это относится и к подтверждению почты, и к сбросу пароля. Оба файла содержат секретные
ссылки и создаются с правами 0600 (где ОС поддерживает эти права). `.local/` исключена из Git.
Папка создаётся автоматически, письма можно удалять после разработки.
Старый общий Email-Verification-Code.txt больше не используется.

### smtp

~~~dotenv
APP_ENV=production
PUBLIC_URL=https://game.example.com
MAIL_DRIVER=smtp
MAIL_FROM=no-reply@example.com
SMTP_ADDR=smtp.example.com:587
SMTP_USERNAME=your-user
SMTP_PASSWORD=your-password
SMTP_TLS_MODE=starttls
SMTP_TIMEOUT=10s
~~~

Замените адреса и учётные данные на реальные. MAIL_FROM должен быть разрешён SMTP-сервером.
Для implicit TLS обычно используются SMTP_TLS_MODE=tls и порт 465.
STARTTLS обязателен в режиме starttls; отсутствие поддержки завершает отправку ошибкой.
Сертификат сервера проверяется. У relay без аутентификации оставьте username/password пустыми.
Секреты задаются в окружении или локальном .env, который исключён из Git.

### Почтовая очередь

Оба драйвера получают письма из таблицы mail_jobs. Регистрация сохраняет аккаунт,
хеш токена и зашифрованное письмо одной транзакцией и возвращает
`201` с `verification_queued: true`. Успех означает постановку в очередь.
Недоступность SMTP не прерывает HTTP-запрос; worker повторяет доставку в фоне.
Если сохранить задание не удалось, транзакция откатывается целиком.
Повторное подтверждение со страницы входа заменяет ссылку и её задание атомарно.

Для API обязателен MAIL_QUEUE_KEY: 32 случайных байта в base64. Сгенерируйте ключ
один раз и сохраните результат в локальном `.env` либо в секретах окружения:

~~~powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
~~~

Содержимое заданий зашифровано AES-256-GCM; ID, тип и срок задания защищены вместе
с содержимым. Ключ хранится отдельно от БД и нужен для восстановления её резервной
копии с незавершёнными письмами. Все экземпляры API должны использовать один ключ.
При старте API проверяет ключ оставшихся непросроченных заданий и останавливается
при несовпадении. Менять ключ можно после остановки всех экземпляров и опустошения
очереди, включая сохранённые ошибки; автоматической ротации ключа нет.

Два worker на экземпляр API захватывают задания через PostgreSQL с арендой на 120 секунд.
Попытка ограничена 70 секундами; простой опрашивается каждые 250 мс. Временные ошибки
повторяются до 8 попыток с задержками 5, 10, 20 секунд и далее, максимум 5 минут.
SMTP 5xx и повреждённое содержимое завершают задание без повторов. При перезапуске
незавершённое задание снова доступно после окончания аренды. Успешные задания удаляются;
окончательные ошибки доступны для очистки через 24 часа или раньше при истечении срока задания.
Просроченные ссылки не отправляются. `npm run cleanup` очищает старые задания.

Доставка допускает повторы: если процесс упал после принятия письма SMTP-сервером,
но до удаления задания, получатель может увидеть дубликат. Message-ID, дата и токен
одинаковы между попытками. Worker завершает работу до закрытия соединений с БД.
Миграция `20261027000200` добавляет только очередь; её откат удаляет оставшиеся задания.

## Конфигурация

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| DATABASE_URL | обязательный | PostgreSQL DSN |
| APP_PORT | 8081 | HTTP-порт |
| APP_ENV | local | production требует HTTPS в PUBLIC_URL |
| PUBLIC_URL | http://localhost:APP_PORT | Адрес сайта в браузере, origin без пути |
| STATIC_DIR | frontend/dist | Каталог собранной SPA |
| TRUSTED_PROXIES | пусто | Доверенные IP/CIDR прокси через запятую для X-Forwarded-For |
| SESSION_TTL | 24h | Серверный срок обычной сессии |
| REMEMBER_ME_TTL | 720h | Серверный срок и срок cookie при «Запомнить меня» |
| VERIFICATION_TTL | 24h | Срок ссылки подтверждения |
| PASSWORD_RESET_TTL | 30m | Срок одноразовой ссылки смены пароля, не больше 24h |
| MAIL_DRIVER | local | local или smtp |
| MAIL_DIR | .local/mail | Каталог локальных писем |
| MAIL_FROM | noreply@example.test | Для SMTP нужен реальный отправитель |
| MAIL_QUEUE_KEY | обязательный | 32 случайных байта в base64 для шифрования очереди |
| SMTP_ADDR | пусто | host:port |
| SMTP_USERNAME | пусто | Логин SMTP; пустое значение отключает SMTP AUTH |
| SMTP_PASSWORD | пусто | Пароль SMTP; используется вместе с SMTP_USERNAME |
| SMTP_TLS_MODE | starttls | starttls или tls |
| SMTP_TIMEOUT | 10s | Ограничение всей отправки |

При входе галочка «Запомнить меня» изначально снята. `POST /api/auth/login` принимает
`{ "email": "player@example.test", "password": "...", "remember_me": true }`.
Без `remember_me`, с `false` или `null` сервер выдаёт сессионную cookie без Expires/Max-Age,
а серверная запись действует не дольше SESSION_TTL. С `true` cookie сохраняется между
запусками браузера, срок cookie и серверной записи задаёт REMEMBER_ME_TTL.
Строки и числа вместо boolean отклоняются; срок нельзя передать в запросе.

Оба срока должны быть положительными, не больше 8760h; REMEMBER_ME_TTL не короче
SESSION_TTL. Срок фиксируется при входе и не продлевается запросами. Изменение настроек
влияет на новые входы; ранее созданные сессии сохраняют свой expires_at.
Cookie Secure включается при HTTPS в PUBLIC_URL; HttpOnly и SameSite=Lax включены всегда.
Logout удаляет cookie и отзывает предъявленную сессию на сервере в обоих режимах.

Закрытие браузера не гарантирует завершение обычной сессии: функция восстановления
вкладок может восстановить и сессионные cookie ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#expiresdate)).
Для явного выхода используйте «Выйти»; серверный срок действует независимо от браузера.
Старый FLASH_SECRET не нужен.

### Восстановление пароля

На странице входа есть ссылка «Забыли пароль?». Форма `/forgot-password` отправляет
`POST /api/auth/forgot-password` с `{ "email": "player@example.test" }`. Для любого
корректного адреса ответ одинаковый: запрос принят, письмо придёт, если аккаунт существует.
IP-лимит общий с остальными публичными auth-запросами; на один аккаунт письмо создаётся
не чаще раза в минуту. После этого новый запрос заменяет предыдущую ссылку.

До поиска аккаунта запрос сохраняется в зашифрованной PostgreSQL-очереди. Лимит —
1024 активных входящих запроса, общий для всех экземпляров API. Переполнение или
ошибка сохранения дают 503 независимо от наличия аккаунта. Worker потребляет запрос,
создаёт хеш токена и исходящее письмо одной транзакцией. Повторная обработка того же
задания не выпускает новый токен. Неизвестный аккаунт и минутный cooldown завершают
задание без письма. Запросы и письма переживают перезапуск; работают local и SMTP.
Ошибки записываются в журнал без адресов, токенов и паролей.

Письмо ведёт на `/reset-password?token=...` через настроенный PUBLIC_URL. GET только
показывает форму. Смена выполняется явным `POST /api/auth/reset-password` с `{ "token": "...",
"password": "..." }`. Пароль вводится дважды, сервер применяет ту же политику 8–72 байта,
что и при регистрации. Ссылка действует PASSWORD_RESET_TTL и используется один раз.
В password_resets хранится хеш токена; его исходное значение до доставки находится
в зашифрованном задании. Неверная, истёкшая и повторная ссылка возвращают
400 с кодом `password_reset_token_invalid`, ошибки пароля — 422 с полем `password`.

Смена пароля, отзыв всех сессий (включая «Запомнить меня»), удаление ссылок сброса и
очистка активного персонажа проходят одной транзакцией. Вход, который успел проверить
старый пароль до сброса, не сможет создать сессию после него. Аккаунт автоматически
не авторизуется и не подтверждает email: для неподтверждённой почты остаётся обычная
проверка письмом. В текущем браузере cookie удаляется, после успеха нужно войти заново.
Уведомление о смене без нового пароля сохраняется в той же транзакции. Сбой сохранения
откатывает смену; сбой доставки обрабатывает worker, уже сохранённый пароль остаётся новым.

Перед запуском обновлённого приложения и cleanup выполните `npm run migrate -- up`:
миграция `20261027000100` добавляет password_resets с индексом срока и каскадом удаления
аккаунта. Откат удаляет ссылки сброса, сохраняя аккаунты, пароли и сессии.
Следующая миграция `20261027000200` добавляет очередь писем.
Базовые решения сверены с [рекомендациями OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

### IP клиента за reverse proxy

Без `TRUSTED_PROXIES` лимитер использует IP соединения (`RemoteAddr`) и игнорирует
заголовки прокси. Loopback и приватные сети автоматически доверенными не становятся.
Для локального прокси можно явно указать `TRUSTED_PROXIES=127.0.0.1/32,::1/128`;
для отдельного сервера — его точный IP или необходимую подсеть. Поддерживаются IPv4,
IPv6 и CIDR через запятую; имена хостов, порты и zone identifiers не принимаются.
Неверная настройка останавливает запуск; её значение в диагностике не выводится.

Только если непосредственный peer доверенный, сервер читает `X-Forwarded-For`
справа налево: пропускает доверенные прокси и останавливается на первом недоверенном
адресе. Всё слева от него игнорируется, включая подставленные клиентом IP.
Повторяющиеся поля заголовка обрабатываются как одна цепочка в порядке получения.
Если вся цепочка доверенная, выбирается её крайний левый адрес.

Прокси должен перезаписывать входящий `X-Forwarded-For` фактическим IP клиента
или дописывать к цепочке адрес своего соединения с клиентом. Не включайте клиентские
сети в доверенные: список обозначает именно узлы, которым разрешено сообщать чужой IP.
В цепочке из нескольких прокси настройте доверие для всех её управляемых узлов.
Если прокси без проверки передаёт заголовок клиента, приложение не сможет отличить подмену.

Пустой/некорректный проверяемый суффикс возвращает лимитер к IP соединения.
Общий размер значений заголовка с разделителями ограничен 4096 байтами;
проверяется максимум 32 адреса справа. Превышение также возвращает IP соединения:
такие запросы за одним прокси делят общий лимит. В заголовке допустимы только IP
без портов, скобок или зон. Эквивалентные IPv6 и IPv4-mapped адреса получают один ключ;
IPv4-mapped CIDR разрешён с длиной от /96 и нормализуется в IPv4. Обычный IPv6 CIDR
не задаёт доверия для IPv4.

`Forwarded`, `X-Real-IP`, `X-Forwarded-Proto` и `X-Forwarded-Host` не используются.
Настройка определяет только IP для лимитера; доверенный origin и Secure cookie
по-прежнему определяет `PUBLIC_URL`. Лимит хранится в памяти каждого процесса:
для нескольких экземпляров приложения потребуется общий лимитер или ограничение на прокси.

### Даты и метаданные записей

Все колонки дат событий используют `timestamptz`: created_at/updated_at,
подтверждение email, активация персонажа, даты наград и сроки действия сессий/токенов.
Они хранят момент времени; часовой пояс соединения влияет на его текстовое
представление, а не на срок действия. В Go сравнивайте моменты через `time.Time.Equal`.

При INSERT created_at и updated_at по умолчанию равны `NOW()` — началу транзакции.
При UPDATE общая функция `set_row_updated_at` обновляет updated_at временем
PostgreSQL (`clock_timestamp()`) только при изменении строки. Запись тех же значений
оставляет дату прежней; изменение одного updated_at считается явным обновлением,
но переданное значение заменяется текущим временем БД. created_at триггер не меняет.
Правило действует для users, sessions, email_verifications, factions, classes,
abilities, characters и таблиц форума, включая прямой SQL. Метаданные откатываются вместе со строкой.
Репозитории не присваивают updated_at; новые таблицы с этим полем должны подключать
такой же триггер в своей миграции. Событийные даты вроде email_verified_at остаются
отдельными значениями и могут отличаться от времени изменения записи.
При создании публикаций форума используется `clock_timestamp()`: антифлуд отсчитывает
интервал от фактической записи после ожидания блокировок, а не от начала транзакции.

Миграция `20261025000600_timestamp_consistency` выполняется транзакционно.
Запускайте её при остановленном API: изменение типов блокирует таблицы, старые
соединения могут держать подготовленные запросы с прежними типами результатов.
Для старых created_at/updated_at/activated_at используется `TimeZone` соединения
миграции — та зона, в которой прежняя БД записывала NOW()/clock_timestamp().
Смена этой настройки перед миграцией без пересчёта данных сдвинет их смысл.

У прежнего кода подтверждения был отдельный путь: email_verified_at и updated_at
записывались одним значением UTC. Поэтому email_verified_at интерпретируется в UTC,
а users.updated_at — в UTC, когда он равен email_verified_at; иначе действует зона
метаданных. Это правило описывает записи текущего приложения. У импортированных
или вручную заданных дат нужно заранее проверить источник зоны и совпадения полей:
timestamp без зоны сам по себе не содержит информации для её восстановления.
В существующие абсолютные expires_at/expired_at миграция не вмешивается.

Откат снимает триггеры и возвращает прежние типы/правила, сохраняя строки и NULL.
Для up/down используйте одну исходную `TimeZone`; откат к timestamp снова теряет
явную привязку к моменту времени (в том числе неоднозначен при переходах летнего времени).
Перед возвратом старого приложения требуется соответствующая версия репозиториев,
которая сама обновляла updated_at.

## API авторизации

Все тела запросов, кроме пустого logout, — JSON; максимальный размер 16 KiB,
для публикаций и действий форума — 64 KiB.
Ответы API не кэшируются. Данные пользователя в ответе: id, email, login, character_id (число или null).

| Метод и маршрут | Вход | Успех |
| --- | --- | --- |
| POST /api/auth/register | email, login, password | 201: message, verification_queued |
| POST /api/auth/login | email, password | 200: user; Set-Cookie |
| GET /api/auth/me | Cookie | 200: user |
| POST /api/auth/logout | Cookie, необязательная | 200: message; удаление cookie |
| POST /api/auth/verify | token | 200: message |
| POST /api/auth/resend-verification | email, password | 200: message |

Для совместимости verify также принимает token в query при пустом теле POST.
При открытии `/verify?token=...` страница автоматически отправляет POST подтверждения,
показывает результат и ссылку на вход. Дополнительная кнопка подтверждения не нужна.
Сам серверный GET только отдаёт страницу. После успеха токен удаляется из адресной
строки, а результат сохраняется при обновлении этой страницы. Повторный запуск эффекта
React не создаёт второй POST; после временной ошибки доступна явная повторная попытка.
Использованная или просроченная ссылка предлагает вход либо запрос нового письма.
На регистрации и форме входа повторная отправка доступна через «Письмо не пришло?»;
она требует почту и пароль. Подтверждение почты само по себе не создаёт сессию.
Logout идемпотентен, в том числе без cookie. Ошибка удаления сессии из БД возвращает 500;
cookie при этом сохраняется, чтобы можно было повторить выход.

Email нормализуется trim + lowercase; login trim, 1–32 символа; новый пароль 8–72 байта.
Вход со старыми короткими паролями сохранён.

Регистрация, вход, подтверждение и resend имеют общий лимит 30 запросов в минуту на IP.
IP берётся из RemoteAddr либо из цепочки X-Forwarded-For согласно TRUSTED_PROXIES
(см. «IP клиента за reverse proxy»). Защита от cross-origin работает независимо от лимита.
Строки истёкших сессий больше не аутентифицируют; их очистка доступна через `npm run cleanup`.

## Ошибки HTTP API

Все ошибки `/api/*`, включая отказы middleware и неизвестные маршруты, используют
один JSON-формат и `Cache-Control: no-store`:

~~~json
{
  "error": "Проверьте заполненные поля",
  "code": "validation_failed",
  "fields": {"password": ["Пароль должен содержать от 8 до 72 байт"]},
  "errors": ["Пароль должен содержать от 8 до 72 байт"]
}
~~~

`error` — сообщение для человека, `code` — стабильный код для логики клиента.
Оба поля обязательны. Необязательный `fields` связывает JSON-имена полей запроса
с массивами сообщений. Для прежних клиентов сохранён `errors`: он автоматически
собирается из `fields` в порядке отсортированных ключей. Без ошибок полей эти два
необязательных поля отсутствуют. Внутренние SQL-ошибки и секреты в ответ не попадают.

| HTTP | code | Значение |
| --- | --- | --- |
| 400 | invalid_json | Некорректный JSON, лишнее поле, не объект или несколько значений |
| 400 | invalid_request | Отсутствующий или неверного типа character_id; ошибка поля character_id |
| 400 | verification_token_invalid | Недействительная или истёкшая ссылка подтверждения |
| 401 | unauthenticated | Нет действующей сессии |
| 401 | invalid_credentials | Неверный email или пароль |
| 403 | email_unverified | Для входа нужно подтвердить email |
| 403 | origin_forbidden | Запрос отклонён защитой от чужого origin |
| 404 | route_not_found | Неизвестный API-маршрут |
| 404 | character_not_found | Персонаж отсутствует или принадлежит другому аккаунту |
| 405 | method_not_allowed | Метод не поддерживается; допустимые методы в Allow |
| 409 | account_conflict | Email или логин занят |
| 409 | email_already_verified | Email уже подтверждён |
| 409 | character_name_taken | Имя персонажа занято; ошибка поля name |
| 413 | request_too_large | Превышен лимит тела: 16 KiB, для форума 64 KiB |
| 415 | unsupported_media_type | Требуется Content-Type: application/json |
| 422 | validation_failed | Неверные значения; подробности по полям в fields |
| 422 | character_class_mismatch | Класс несовместим с фракцией; ошибка поля class_id |
| 429 | rate_limited | Частые запросы; задержка повтора в Retry-After |
| 500 | internal_error | Внутренняя ошибка без технических подробностей |
| 503 | password_reset_unavailable | Не удалось сохранить запрос восстановления пароля |

Успешная регистрация означает, что аккаунт и задание подтверждения сохранены:
`201` и `verification_queued: true`. Повторная регистрация для восстановления доставки не нужна.

Frontend показывает ошибки регистрации и создания персонажа рядом с соответствующими
полями и убирает их при редактировании. Подсказка о подтверждении почты появляется только
для `403/email_unverified`. `401/unauthenticated` завершает локальное состояние сессии,
а `401/invalid_credentials` не сбрасывает уже действующий аккаунт. Для старых ответов
без code/fields сохраняются общие сообщения и прежняя обработка 401.

## Миграция авторизации

20261025000100_auth_hardening.up.sql:
- расширяет email до 254 символов и добавляет уникальность нормализованного адреса;
- переводит срок подтверждения в timestamptz и добавляет expires_at сессий;
- хеширует существующие токены, сохраняя возможность использовать исходные ссылки/cookie;
- ограничивает старые сессии сроком created_at + 168 часов.

Для старых timestamp используется TimeZone сессии миграции: задайте ту же зону,
в которой создавались прежние строки. Совпадения адресов после trim/lower останавливают
миграцию целиком, без удаления аккаунтов. Предварительная проверка:

~~~sql
SELECT lower(btrim(email)), count(*)
FROM users
GROUP BY lower(btrim(email))
HAVING count(*) > 1;
~~~

Down-миграция отзывает сессии и ссылки: исходные токены невозможно восстановить из хешей.
Если уже есть email длиннее 32 символов, rollback останавливается, чтобы не усечь данные.
Миграция использует встроенную функцию [sha256 PostgreSQL](https://www.postgresql.org/docs/12/functions-binarystring.html).

Интерфейс целиком находится во frontend: Go отдаёт собранную SPA из frontend/dist.
Состояние аккаунта подключается к React через Context и useSyncExternalStore.

Зависимости frontend идут от app к features, entities и shared. Модули features используют
entities/shared; shared не зависит от доменных модулей. AccountStore получает HTTP-операции
через интерфейс: AccountProvider подключает методы auth/character API при сборке приложения.
Store остаётся единственным источником состояния аккаунта и выбранного персонажа;
импортирует из entities/character только типы списка и персонажей. Это сохраняет общую
обработку истёкшей сессии, объединение обновлений и защиту от запоздавших ответов.

Все запросы используют shared/api/client с путями `/api/...` из OpenAPI; вызовы конкретных
операций находятся в features/*/api.ts. Признак неподтверждённого email принадлежит features/auth/errors,
а общий разбор HTTP-ошибок — shared/api/errors. Общего файла всех моделей и API-вызовов нет.

ESLint проверяет статические импорты: запрещает зависимости shared/entities от верхних
слоёв, features от app и прямые зависимости между текущими auth/character-модулями.
При добавлении нового feature расширьте эти правила. Новые маршруты подключайте в
app/App.tsx; специфичные экран и API размещайте в своём feature, общие контракты —
в соответствующей entity. Тесты сохраняйте в корневом tests/frontend.

Реквизиты входа отделены от данных текущего аккаунта. `auth.Credentials` содержит
хеш пароля и загружается только для проверки пароля при login/resend. `auth.Identity`
содержит ID аккаунта, роль, nullable ID персонажа, email, логин и отметку подтверждения email.
Именно Identity возвращается из авторизации и передаётся в HTTP-контекст; запрос сессии
не читает пароль, профиль или даты создания/обновления аккаунта. Ответ API строится
отдельным DTO с четырьмя публичными полями, перечисленными выше.

Запись регистрации передаётся в репозиторий структурой `auth.Registration`
с именованными полями и готовыми хешами. Аккаунт и подтверждение по-прежнему сохраняются
одной транзакцией. Типами данных владеют использующие их предметные модули;
репозитории читают SQL-результаты в эти контракты. Общего пакета моделей, повторяющих все
таблицы БД, нет. Тестовый auth-репозиторий также использует Credentials и Identity,
а интеграционные проверки nullable-полей вызывают действующие методы репозиториев.

Тесты SQL не используют DATABASE_URL приложения. Каждый создаёт случайную отдельную схему,
применяет миграции и удаляет свою схему после завершения; учётной записи нужны соответствующие права.
Без TEST_DATABASE_URL локально эти тесты явно пропускаются; в CI или обязательном режиме
это ошибка. SMTP-тесты используют только локальный
тестовый сервер с тестовыми сертификатами и не отправляют настоящую почту.

Тесты seed собирают настоящую CLI-команду, запускают её в отдельных временных папках
и проверяют повторный/параллельный запуск, смещённые ID, сохранение настроенного баланса,
откат при ошибке и таймауте, независимость от HTTP/SMTP и миграцию существующих данных.

Для браузерной проверки соберите frontend, задайте TEST_DATABASE_URL как выше и путь
к Chrome/Chromium/Edge. Проект использует Node.js 24+ с встроенным WebSocket:

~~~powershell
$env:CHARACTER_BROWSER_BINARY = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
go test -count=1 -run TestCharacterBrowserFlow -v ./tests/db
~~~

Тест открывает временный HTTP-сервер и отдельный headless-профиль браузера, проверяет
ошибки полей и их сброс при редактировании, разные причины 403, создание и фильтрацию
классов, конфликт имени, выбор после перезагрузки и два независимых сеанса.
Используется временная SQL-схема; обычные аккаунты и профиль браузера не затрагиваются.
Без CHARACTER_BROWSER_BINARY браузерный тест локально пропускается, а в CI/обязательном
режиме завершается ошибкой. Для сохранения снимков можно задать CHARACTER_SCREENSHOT_DIR
внутри `.local/`: npm-команды разрешают относительный путь от корня проекта;
для прямого go test используйте абсолютный путь. `npm run check` сам собирает frontend
перед браузерной проверкой.

### Нагрузочная проверка боёв

`npm run test:combat-load` загружает только `.env.test`, требует TEST_DATABASE_URL
и запускает `BenchmarkCombatLoad` из `tests/db`. Обычный `npm run check` включает
только маленькую проверку стенда; тяжёлые измерения запускаются явно.

Для каждой из ступеней 100/500/1000 создаются отдельная случайная схема и два сценария:

- `burst`: первая атака всех NPC назначена на одно время; измеряется обработка всплеска.
- `mixed`: атаки распределены во времени, каждый аккаунт читает текущий бой, журнал
  и умения каждые 2 s и применяет умение каждые 3 s. Окно по умолчанию 15 s;
  переменная COMBAT_LOAD_DURATION задаёт от 5 s до 1 m.

Работают реальные два исполнителя и настроенный пул PostgreSQL. HTTP проходит через
локальный тестовый сервер с настоящими маршрутами, авторизацией и репозиториями.
Генератор имеет 64 HTTP-исполнителя и очередь на 256 запросов. При переполнении он
считает пропуски; расписание не замедляется вслед за ответами. Время от запланированного
запроса до ответа включает ожидание в генераторе и очереди. Вывод содержит JSON-строки
`COMBAT_LOAD_RESULT`: p50/p95/p99/max, статусы/ошибки/пропуски HTTP, задержку записи NPC,
выборки длины/возраста очереди, ожидание пула и количество сохранённых команд.

HP синтетических персонажей и NPC увеличены до 100000 для сохранения боёв в течение
окна; паттерн обычного NPC уровня 1, урон/цена/кулдауны умения и регенерация сохраняются.
После остановки всех клиентов и исполнителей проверяется целостность журнала,
команд и исходов, затем удаляется только схема этого сценария. Сервер ожидает
завершения обработчиков даже после таймаута клиента. Каждый ключ команды сверяется
с квитанцией в БД; неопределённые результаты (обрыв ответа или HTTP 5xx) отдельно
учитываются в `command_evidence`, не скрывая потерю подтверждённых команд.
HP, MP, дробные остатки регенерации и здоровье NPC восстанавливаются по журналу
и сравниваются с сохранёнными значениями. Таймаут операции исполнителя считается
ошибкой нагрузки; штатная остановка самого исполнителя в ошибки не входит.

Это измерение серверного кода и loopback HTTP на конкретной машине. Генератор делит
процесс/CPU с сервером; браузер, WebSocket, реальная сеть и длительное накопление
истории в него не входят. Чтение журнала начинается с нулевого курсора. Задержка NPC
считается от игрового occurred_at до created_at записи события, без обещания времени
commit или отображения в браузере. Снимки очереди делаются раз в 250 ms и могут
пропускать короткие пики. Нагрузочные показатели сами по себе не объявляют сценарий
успешным по SLA; отдельно проверяйте ошибки/пропуски и оставшуюся очередь.
