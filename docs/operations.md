# Обслуживание проекта

Команды выполняются из корня проекта. После `npm run build` для сервера доступны
`.local/bin/cleanup`, `.local/bin/mailqueue` и `.local/bin/dbbackup` (на Windows — `.exe`).
Они читают необязательный `.env` из рабочей папки; переменные процесса имеют приоритет.
Для запуска по расписанию используйте собранные бинарники и фиксированную рабочую папку.

## Состояние почты

```sh
npm run mail:status
npm run cleanup -- -dry-run
npm run cleanup -- -batch-size 1000 -timeout 1m
```

`mail:status` требует только DATABASE_URL. Команда не читает почтовый ключ, не забирает
задания и не изменяет данные. JSON-событие `mail_queue_status` содержит время PostgreSQL
`cutoff` и следующие поля:

| Поле | Значение |
| --- | --- |
| total | Все задания в таблице |
| pending | Неистёкшие задания, ожидающие доступной попытки |
| due | Часть pending, которую уже можно отправлять |
| leased | Неистёкшие задания с действующей арендой worker, включая последнюю попытку |
| failed | Неистёкшие окончательно ошибочные задания, включая исчерпанные попытки без активной аренды |
| expired | Задания с истёкшим сроком, независимо от прежнего состояния |
| oldest_pending_age_seconds | Возраст самого старого pending с момента создания; null, если очередь ожидания пуста |

`pending + leased + failed + expired = total`; `due` входит в pending. Все категории
считаются одним запросом относительно одной отметки времени. Email, токены и содержимое
писем не выводятся. Ошибка соединения или чтения даёт ненулевой exit code.

Проверяйте очередь раз в минуту внешним мониторингом. Рост due и возраста pending в нескольких
последовательных проверках — повод проверить worker и события `mail_*` в журнале приложения.
Любой failed требует проверки доставки/конфигурации. Expired должны убывать после cleanup;
задания с ещё действующей арендой очистка оставляет до следующего прохода. Разовый нулевой
due не доказывает доставку всех писем: смотрите также failed, expired и журнал worker.

## Резервная копия

Установите `pg_dump` и `pg_restore` той же основной версии, что PostgreSQL сервера.
Укажите POSTGRES_BIN_DIR, например `C:/Program Files/PostgreSQL/18/bin` или
`/usr/lib/postgresql/18/bin`; пустое значение использует PATH. Инструменты запускаются
без оболочки. Пароль передаётся через временный приватный pgpass-файл, удаляемый после работы,
а не через аргументы процесса. Диагностика инструментов с реквизитами в журнал не попадает.

Нужны DATABASE_URL и существующий MAIL_QUEUE_KEY приложения. Ключ должен расшифровывать
неистёкшие задания; миграции должны быть в чистом состоянии. Копируется вся БД, поэтому
роль должна читать все её таблицы и последовательности. Каталог родителя создайте заранее:

```powershell
New-Item -ItemType Directory -Force .local/backups | Out-Null
$backupStamp = (Get-Date).ToUniversalTime().ToString('yyyyMMddTHHmmssfffZ')
npm run db:backup -- -dir ".local/backups/$backupStamp" -timeout 5m
```

```sh
mkdir -p .local/backups
npm run db:backup -- -dir ".local/backups/$(date -u +%Y%m%dT%H%M%SZ)" -timeout 5m
```

Команда отказывается перезаписывать существующий каталог. В новом каталоге находятся
`database.dump` в custom-формате PostgreSQL и завершающий `manifest.json`: версия формата,
время, имя исходной БД, версия миграции, отпечаток ключа и SHA-256 архива. Самого ключа
и реквизитов подключения в manifest нет. Архив и метаданные используют один согласованный
снимок БД; работа приложения может продолжаться. Успех отмечается `backup_completed`.
Неполная копия без корректного manifest не принимается для восстановления.

Храните MAIL_QUEUE_KEY **отдельно от архива**, в менеджере секретов или отдельном защищённом
хранилище с собственной резервной копией. Сохраните связь версии ключа с key_id в manifest.
Новый случайный ключ не расшифрует старую очередь. Перед переносом зафиксируйте также версию
приложения, конфигурацию без секретов и способ получения DATABASE_URL/SMTP-настроек.

На Linux каталоги и файлы создаются с правами 0700/0600. На Windows заранее ограничьте ACL
папок копий и TEMP учётной записью сервиса и администраторами: Unix mode не заменяет NTFS ACL.
Архив содержит данные аккаунтов и хеши паролей; копируйте его в защищённое хранилище вне
сервера. Локальная `.local/backups` исключена из Git и подходит для разработки, но сама по
себе не защищает от потери диска. Практический начальный retention — 14 ежедневных и
8 еженедельных копий; удаление старых копий включайте только после успешного копирования
и проверки восстановления. Эти команды ничего автоматически не удаляют.

## Восстановление и проверка

Восстанавливайте только собственные доверенные архивы: PostgreSQL-архив может содержать
исполняемый SQL. SHA-256 обнаруживает повреждение, но не подтверждает происхождение файла.

1. Подготовьте **новую пустую отдельную БД** совместимой версии PostgreSQL, UTF8 и ICU.
   Её имя должно отличаться от исходного даже при восстановлении на другом сервере.
   Приложение и другие писатели не должны подключаться к этой БД во время процедуры.
2. Передайте её URL как RESTORE_DATABASE_URL через защищённое окружение или локальный
   `.env`. Команда никогда не подставляет DATABASE_URL вместо цели. Восстановите исходный
   MAIL_QUEUE_KEY из отдельного хранилища; задайте POSTGRES_BIN_DIR.
3. Запустите `npm run db:restore -- -dir .local/backups/ИМЯ-КОПИИ -timeout 5m`.
   Для сервера без Node: `.local/bin/dbbackup restore -dir /secure/backups/ИМЯ-КОПИИ`.
4. Дождитесь `restore_completed` и exit code 0. Проверяются checksum, совпадение ключа,
   пустота цели, чистая версия миграций и расшифровка неистёкших писем. Два параллельных
   запуска восстановления в одну цель разделены блокировкой; второй получит отказ.
5. Запустите совместимую с копией версию приложения с целевой БД, `MAIL_DRIVER=local` и
   отдельной MAIL_DIR. Проверьте readiness, вход, выбор персонажа и состояние очереди.
   Ссылки и сессии из старой копии сохраняют исходные сроки и могли уже истечь.
   После проверки остановите пробный экземпляр. Переключение боевого приложения — отдельная
   операция после проверки данных, миграций и конфигурации.

Восстановление не создаёт БД, не использует `--clean` и не удаляет существующие объекты.
Ранее существующие таблицы, схемы, типы, функции, расширения, большие объекты,
публикации/подписки репликации и другие пользовательские объекты дают отказ. Требуются
штатные системные схемы без ручных модификаций. pg_restore
работает в одной транзакции; при SQL-ошибке изменения откатываются. При обрыве связи или
отмене около commit исход может быть неизвестен: проверьте цель, не удаляйте её вслепую.
Код ошибки или отсутствие `restore_completed` означает, что проверка не закончилась успешно.

Допустим полностью заданный PostgreSQL URL с host, user и database; пароль необязателен,
порт по умолчанию 5432. Поддержаны sslmode, sslrootcert, sslcert+sslkey, connect_timeout и
channel_binding. Для verify-ca/verify-full задавайте доверенный sslrootcert явно. Неявные
PG*-переменные, сервисы libpq, несколько хостов, параметры схемы и неподдерживаемые TLS/CRL
опции отвергаются, чтобы pgx и pg_dump/pg_restore использовали одинаковое подключение.

Реальный тест в `tests/backup` создаёт собственные временные БД, применяет миграции,
сохраняет и восстанавливает данные с зашифрованным письмом и проверяет защитные отказы.
Он входит в `npm run check` и `npm run test:race`; приложение пользователя не используется.
Повторяйте отдельную пробу восстановления копии из внешнего хранилища после изменения
схемы/ключа/версии PostgreSQL и регулярно, например раз в месяц: CI не проверяет доступность
вашего внешнего хранилища или сохранность его ключей.

## Роли и модерация

Новые и существующие аккаунты по умолчанию имеют роль `user`. Роль привязана к аккаунту,
а сообщения отправляются от выбранного персонажа. Для первого администратора или
назначения модератора используйте явный ID аккаунта (поле `user.id` в `/api/auth/me`):

```powershell
go run ./cmd/accountrole -user-id 123 -role administrator
go run ./cmd/accountrole -user-id 456 -role moderator
go run ./cmd/accountrole -user-id 456 -role user
```

Замените ID в примерах. Команда читает `DATABASE_URL` из окружения или `.env`; можно
указать `-env-file path`. Она не требует почтовой конфигурации, блокирует строку аккаунта
на время изменения и сохраняет смену роли в журнале. `actor_user_id=NULL` означает
локальное административное действие. Повторное назначение той же роли ничего не меняет.
Обновите страницу после назначения: действующие сессии получают актуальные права
на следующем запросе. Публичного API назначения ролей нет.

Чат: `/chat`. Журнал и управление ограничениями: `/moderation`. Модератор может
удалять сообщения и выдавать/снимать chat/forum-баны обычным пользователям.
Администратор также управляет account-банами и может модерировать другие служебные
аккаунты. Самоблокировка запрещена. Временный бан длится от 1 до 168 часов;
бессрочным бывает только бан аккаунта. Причина выдачи, снятия или удаления обязательна.
Истечение проверяется по времени PostgreSQL и не зависит от cleanup.

Внизу чата и под списком разделов форума находится ссылка «Список модераторов»
(`/chat/moderators`). Список доступен всем авторизованным игрокам и содержит только
аккаунты с ролью `moderator`, без администраторов: одна строка на аккаунт, его логин,
роль и выбранный персонаж.
Email и журнал нарушений туда не попадают. Неподтвержденные и заблокированные целиком
аккаунты в список не входят. В чате и форуме ники администраторов выделяются мягким
красным, модераторов — зеленым; в истории чата используется текущая роль,
а имя персонажа сохраняется исходным.

Ники авторов в чате и форуме открывают `/characters/:characterId`. Ссылка использует
персонажа публикации, а не текущий выбор его владельца. В каталоге модераторов ссылки
появляются при выбранном персонаже; `character_id` и `character_name` иначе равны null.
Публичный профиль доступен только вошедшим игрокам, не меняет выбор персонажа и
показывает имя, портрет, фракцию, класс, уровень и текущую роль аккаунта. Приватные
данные аккаунта, опыт и ресурсы не входят в GET `/api/characters/profile?character_id=ID`.

Chat-бан сохраняет чтение и ограничивает отправку всеми персонажами аккаунта.
Forum-бан запрещает создание и редактирование публикаций форума, сохраняя чтение.
Он не ограничивает чат; chat-бан, в свою очередь, не ограничивает форум.
Account-бан отзывает все сессии и активного персонажа в одной транзакции, запрещает
новый вход; сброс пароля не снимает бан. После снятия нужно войти заново.
Удаленные сообщения выдаются клиентам как заглушки, исходный текст остается в БД.

Текущий WebSocket hub работает в одном процессе API. Он передает уведомления об
изменениях, а данные клиент получает через авторизованные HTTP-запросы. Для нескольких
экземпляров API понадобится общий источник событий. Reverse proxy должен пропускать
WebSocket Upgrade для `/api/chat/events`, сохранять `Origin` и использовать idle timeout
больше 30 секунд. Vite уже включает WS proxy. Не включайте переписывание Origin:
сервер принимает только текущий origin или `PUBLIC_URL`.

## Форум

Вход: `/forum`. Начальные разделы — Новости, Общение, Помощь и Предложения.
Темы в Новостях создаёт только администратор; отвечать могут обычные игроки.
Разделы хранятся в `forum_categories`; экран управления ими появится с админкой.

Читать можно без выбранного персонажа. Для создания и редактирования нужен активный
персонаж. Имя автора сохраняется при публикации; редактирование своим аккаунтом с
другого персонажа не меняет исходного автора. Цвет ника соответствует текущей роли
аккаунта. Заголовок: 3–120 символов, текст: 1–10000, без HTML-разметки. Создание тем и
ответов ограничено одним действием в пять секунд на аккаунт; скрытие не обходит лимит.
JSON-запросы форума ограничены 64 КБ; у остальных маршрутов сохраняется лимит 16 КБ.

Модератор скрывает/восстанавливает публикации обычных игроков и свои, закрывает/
открывает и закрепляет темы; администратор может модерировать всех. Причина действия
обязательна, запись появляется в общем журнале. Скрытая тема недоступна игрокам даже
по прямой ссылке; скрытые ответы отображаются заглушками. Сотрудники могут проверить
исходный текст. Восстановление темы не восстанавливает отдельно скрытые ответы.

Закрытая тема запрещает новые ответы и пользовательские изменения до открытия.
Редактирование проверяет `version`: при конфликте интерфейс сохраняет черновик и
предлагает обновить запись, не перезаписывая чужое изменение автоматически.
После обновления сравните тексты и нажмите «Продолжить с моим текстом», затем
сохраните изменения. Само обновление и подтверждение ничего не публикуют.
Переключение аккаунта/персонажа сбрасывает формы и отменяет устаревшие запросы.

## Расписание

Пока хостинг не выбран, следующие настройки остаются примерами; задания автоматически
не регистрируются. Начальные интервалы: cleanup каждый час, backup ежедневно, состояние
очереди раз в минуту. Ненулевые коды завершения должны попадать в мониторинг.

Linux cron, от отдельного пользователя приложения. Заранее создайте закрытые каталоги
`/srv/gotest-backups` и журналов; `.env` доступен только этой учётной записи:

```cron
SHELL=/bin/sh
0 * * * * cd /srv/gotest && .local/bin/cleanup -timeout 1m >> /srv/gotest-logs/cleanup.log 2>&1
15 3 * * * cd /srv/gotest && .local/bin/dbbackup backup -dir "/srv/gotest-backups/$(date -u +\%Y\%m\%dT\%H\%M\%SZ)" -timeout 5m >> /srv/gotest-logs/backup.log 2>&1
* * * * * cd /srv/gotest && .local/bin/mailqueue -timeout 10s >> /srv/gotest-logs/mailqueue.log 2>&1
```

Для cron проценты в `date` экранированы. Включите ротацию журналов и отправку ошибки
задания в используемый мониторинг. Если секреты выдаёт менеджер окружения, подключите
его к сервису/задаче вместо записи секретов в crontab.

Windows Task Scheduler: cleanup запускает `C:\srv\gotest\.local\bin\cleanup.exe`
с аргументами `-timeout 1m` и рабочей папкой `C:\srv\gotest`, повтор каждый час.
Для ежедневной копии сохраните следующий скрипт в закрытой локальной папке и настройте
действие `powershell.exe -NoProfile -NonInteractive -File C:\srv\ops\backup.ps1`:

```powershell
$ErrorActionPreference = 'Stop'
Set-Location -LiteralPath 'C:\srv\gotest'
$backupStamp = (Get-Date).ToUniversalTime().ToString('yyyyMMddTHHmmssfffZ')
$backupPath = Join-Path 'D:\gotest-backups' $backupStamp
& '.local\bin\dbbackup.exe' backup -dir $backupPath -timeout 5m 2>> 'D:\gotest-logs\backup.log'
exit $LASTEXITCODE
```

Задача работает от выделенной учётной записи с правами на конфигурацию, TEMP и каталог
копий; пароли и ключи не помещаются в аргументы задачи. Проверяйте Last Run Result,
событие завершения и появление полной копии. Перенос во внешнее хранилище и retention
настраиваются в выбранной инфраструктуре после проверки доступа и восстановления.
